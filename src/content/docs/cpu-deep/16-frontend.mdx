## 파이프라인의 앞부분 — 프런트엔드

3장의 파이프라인을 현대 CPU 구조에 맞춰 조금 더 자세히 나눠 보겠습니다.
CPU 파이프라인은 크게 두 부분으로 볼 수 있습니다.

- **프런트엔드**(front end) — 명령어를 가져오고 디코드해 뒤쪽 실행 단계가 계속 일할 수 있도록 공급합니다
- **백엔드**(back end) — 전달받은 명령어를 비순차 실행 구조(3장)를 이용해 실제로 처리합니다

둘 중 느린 쪽이 전체 성능을 제한합니다.
3장에서 본 의존성 체인은 주로 백엔드 문제였습니다.
분기 예측 실패는 뒤에서 설명할 top-down 분류에서는 별도의 "잘못된 추측" 범주로 다룹니다.
프런트엔드에도 고유한 구조와 병목이 있습니다.

- **디코드** — 특히 x86-64 명령어는 길이가 1~15바이트로 가변적입니다.
  어디서 한 명령어가 끝나는지 찾는 것부터 복잡합니다.
  CPU는 이를 **μop**(micro-operation, 마이크로연산)이라는 고정 형태의 내부 명령어로 분해하고 이후에는 μop 흐름으로 처리합니다
- **μop 캐시** — 이미 디코드한 μop를 저장하는 전용 캐시입니다.
  작은 핫 루프는 디코드 단계를 거의 건너뛰고 반복할 수 있습니다
- **명령어 캐시(L1i)와 iTLB** — 명령어도 메모리에 있으므로 데이터와 마찬가지로 캐시([2장](/cpu/02-memory-hierarchy/))와 주소 변환([14장](/cpu-deep/14-virtual-memory/))을 거칩니다.
  L1 명령어 캐시는 보통 수십 KB 규모입니다

## 분기 목적지 예측 — BTB

3장에서 본 분기 예측은 "분기를 할 것인가 말 것인가"를 맞히는 문제였습니다.
프런트엔드에는 또 하나의 예측이 있습니다. 바로 **어디로 이동할지**입니다.

분기 목적지 주소는 명령어를 디코드한 뒤에야 알 수 있습니다.
하지만 페치 단계는 디코드보다 앞서 움직여야 합니다.
그래서 CPU는 **BTB**(branch target buffer)라는 구조에
"이 분기 명령어는 최근에 어디로 이동했는가"를 저장해 둡니다.
현대 CPU는 여기에 분기 이력 패턴을 이용해 간접 분기의 목적지도 예측하는 구조를 함께 사용합니다.

이 구조가 특히 중요해지는 곳이 **간접 분기**(indirect branch)입니다.
분기 목적지가 레지스터나 메모리 값에 따라 달라지는 형태입니다.
Rust에서는 함수 포인터 호출, `dyn Trait`의 vtable 호출([7장](/rust-opt/07-zero-cost/)),
큰 `match`가 만드는 점프 테이블, 인터프리터의 명령어 디스패치 등이 여기에 해당합니다.
목적지가 계속 같거나 규칙적이면 BTB와 예측기가 잘 맞힐 수 있습니다.
반대로 목적지가 계속 불규칙하게 바뀌면 예측 실패가 반복되고 파이프라인을 비우는 비용을 지불합니다.

실험해 보겠습니다. 내부 동작이 비슷한 함수 16개를 함수 포인터 배열에 넣고
규칙적인 순서로 호출하는 경우와 무작위 순서로 호출하는 경우를 비교합니다.
호출 횟수는 같습니다.

따라서 `dyn`의 비용은 호출 대상이 어떤 순서로 등장하는지에도 영향을 받습니다.

## 코드 크기도 성능 자원입니다

프런트엔드 관점에서 보면 [6장](/rust-opt/06-compiler/)에서
`#[inline(always)]`를 남용하면 오히려 느려질 수 있다고 한 이유가 분명해집니다.

인라이닝은 함수 본문을 복제합니다.
너무 많은 함수를 한 핫 경로에 펼치면 코드가 L1i와 μop 캐시를 넘어서고,
프런트엔드가 명령어를 충분히 빠르게 공급하지 못할 수 있습니다.
그러면 뒤쪽 실행 유닛이 일할 준비가 되어 있어도 명령어를 기다리게 됩니다.
데이터 캐시 미스와 비슷한 구조의 문제가 명령어 쪽에서도 일어나는 셈입니다.

코드 크기를 조절할 때 사용할 수 있는 도구는 다음과 같습니다.

- `opt-level = "s"` / `"z"`(6장) — 코드 크기를 우선하는 최적화 설정입니다
- `#[cold]`와 `#[inline(never)]` — 오류 처리처럼 거의 실행되지 않는 코드를 핫 경로와 분리하도록 힌트를 줍니다.
  컴파일러도 패닉 경로 등을 비슷하게 다루는 경우가 많습니다
- PGO([21장](/rust-deep/21-build-control/)) — 실제 실행 프로파일을 이용해 핫/콜드 코드 배치를 최적화합니다.
  PGO 성능 향상의 상당 부분은 이런 프런트엔드 효율 개선에서 나오기도 합니다

## top-down 분석 — 병목을 네 가지로 나누기

지금까지 살펴본 구조를 합치면 CPU 성능을 제한하는 후보가 많습니다.
이를 체계적으로 나눠 보는 방법이 **top-down 분석**(top-down microarchitecture analysis)입니다.

핵심 아이디어는 간단합니다.
CPU가 한 사이클에 처리할 수 있는 μop 발행 슬롯 전체를 기준으로
각 슬롯이 어떤 상태였는지 네 가지 범주로 나눕니다.

| 분류 | 의미 | 관련 내용 |
| --- | --- | --- |
| **Retiring** | 실제로 유효한 작업이 완료됨 | 좋은 상태입니다. 더 줄이려면 명령어 자체를 줄이거나 SIMD를 고려합니다([4장](/cpu/04-simd/)) |
| **Bad Speculation** | 잘못 추측해 실행한 작업을 버림 | 분기 예측 실패([3장](/cpu/03-pipeline/)), 이 장의 간접 분기 |
| **Frontend Bound** | 명령어 공급이 부족함 | 이 장의 L1i, μop 캐시, 디코드 문제 |
| **Backend Bound** | 실행 자원 또는 데이터 대기로 막힘 | Memory Bound([2장](/cpu/02-memory-hierarchy/), [14장](/cpu-deep/14-virtual-memory/), [15장](/cpu-deep/15-cache-internals/))와 Core Bound([3장](/cpu/03-pipeline/))로 더 나눌 수 있습니다 |

[8장](/rust-opt/08-measure/)에서 "IPC가 낮다면 무언가를 기다리고 있다"고 설명했습니다.
top-down 분석은 그 "무언가"를 성능 카운터로 분류하는 방법입니다.
Linux의 `perf`에서는 이 분류를 직접 볼 수 있습니다.

```text
$ perf stat -M TopdownL1 ./target/release/myapp

    18.5 %  tma_frontend_bound
     4.2 %  tma_bad_speculation
    51.8 %  tma_backend_bound
    25.5 %  tma_retiring
```

이 예에서는 Backend Bound가 절반이 넘습니다.
그렇다면 다음 단계에서는 Memory Bound와 Core Bound를 더 자세히 보는 `TopdownL2` 수준으로 내려갑니다.
이처럼 큰 범주에서 작은 범주로 내려가며 분석하기 때문에 top-down이라는 이름이 붙었습니다.
개별 하드웨어 이벤트를 처음부터 무작정 들여다보는 것보다 진단 방향을 잡기 쉽습니다.
macOS에서는 Instruments의 CPU Counters에서 비슷한 정보를 확인할 수 있습니다.

## 정리

- CPU 프런트엔드는 명령어를 공급합니다. x86-64에서는 가변 길이 명령어를 μop로 분해하고 μop 캐시로 재디코드 비용을 줄입니다
- 분기에는 "방향"뿐 아니라 "목적지" 예측도 있습니다. 간접 호출은 목적지가 불규칙할 때 느려질 수 있으며 실험에서는 약 3.4배 차이가 났습니다
- 코드 크기는 성능 자원입니다. 과도한 인라이닝은 L1i와 μop 캐시를 압박할 수 있습니다. `#[cold]`와 PGO가 도움이 될 수 있습니다
- top-down 분석은 병목을 Retiring, Bad Speculation, Frontend Bound, Backend Bound의 네 범주로 나눠 진단합니다
