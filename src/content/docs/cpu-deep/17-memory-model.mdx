## 재배치의 원인 — 스토어 버퍼

[3장](/cpu/03-pipeline/)에서 CPU가 명령어를 비순차 실행한다고 배웠습니다.
하지만 메모리 **쓰기**에는 별도의 구조가 하나 더 있습니다.

쓰기는 곧바로 L1 캐시에 반영되지 않을 수 있습니다.
먼저 코어 내부의 대기열인 **스토어 버퍼**(store buffer)에 들어가고,
CPU는 해당 쓰기가 캐시에 완전히 반영될 때까지 기다리지 않고 다음 명령어를 진행할 수 있습니다.
버퍼의 내용은 이후 적절한 시점에 L1 캐시로 흘러갑니다.
[5장](/cpu/05-multicore/)에서 보았듯이 쓰기에는 캐시 라인의 배타적 소유권을 얻는 과정이 필요하므로,
스토어 버퍼는 이 지연 시간을 숨기는 데 매우 효과적입니다.

같은 코어는 스토어 버퍼 안에 있는 자신의 값을 바로 읽을 수 있습니다.
이를 store-to-load forwarding이라고 부릅니다.
그래서 단일 스레드에서는 이상한 동작이 보이지 않습니다.
문제는 다른 코어입니다. **스토어 버퍼 안에 머무르는 동안 그 쓰기는 다른 코어에서 아직 보이지 않을 수 있습니다.**

이 때문에 프로그램 순서상 먼저 나온 쓰기가 다른 코어에 보이기 전에,
그 뒤의 읽기가 먼저 관측되는 것처럼 보일 수 있습니다.
즉 **스토어→로드 재배치**가 발생합니다.

## 실험 — 실제 재배치를 관측하기

고전적인 리트머스 테스트로 직접 확인해 보겠습니다.

- 스레드 A: `X = 1`을 쓴 다음 `Y`를 읽습니다
- 스레드 B: `Y = 1`을 쓴 다음 `X`를 읽습니다

모든 메모리 연산이 프로그램에 적힌 순서대로 다른 코어에 보인다면
두 스레드가 **동시에 0을 읽는 결과는 나올 수 없습니다**.
20만 번 반복해서 확인합니다.

<RustPlay code={litmus} mode="release" title="논리적으로 불가능해 보이는 결과는 몇 번 나올까?" />

저자가 Playground에서 측정했을 때 `Relaxed`에서는 20만 번 중 **13,122번**
두 스레드가 모두 0을 읽는 결과가 나왔습니다. 약 6.6%입니다.
`SeqCst`로 바꾸면 0번이 됩니다.

두 스레드의 쓰기가 각각 자신의 스토어 버퍼에 머무는 동안
상대방 변수의 이전 값인 0을 읽을 수 있기 때문입니다.
`SeqCst`는 필요한 장벽이나 더 강한 명령어를 사용해 이런 순서 뒤집힘이 관측되지 않도록 막습니다.

여기서 두 가지를 꼭 구분해야 합니다.
첫째, 이것은 컴파일러 최적화([6장](/rust-opt/06-compiler/))만의 문제가 아닙니다.
기계어 명령 순서가 그대로여도 CPU 하드웨어 자체가 메모리 연산의 가시 순서를 바꿀 수 있습니다.
`Ordering`은 컴파일러와 CPU **양쪽**에 제약을 줍니다.
둘째, 이 실험은 x86에서도 나타납니다.
"x86은 메모리 순서가 강하다"고 알려져 있지만 스토어→로드 재배치는 허용됩니다.

## 하드웨어 메모리 모델

CPU가 어떤 메모리 순서 변경을 허용하는지를 **메모리 모델**(memory model)이라고 부릅니다.
대표적인 아키텍처를 비교하면 다음과 같습니다.

| | x86-64 (TSO) | ARM64 (weak) | RISC-V (weak) |
| --- | --- | --- | --- |
| 스토어→로드 | 재배치 가능 | 재배치 가능 | 재배치 가능 |
| 로드→로드 | 순서 유지 | 재배치 가능 | 재배치 가능 |
| 스토어→스토어 | 순서 유지 | 재배치 가능 | 재배치 가능 |
| Acquire/Release 구현 | 일반적인 load/store로 가능한 경우가 많음 | 전용 명령어(`ldar`/`stlr`) | fence나 명령어 속성 사용 |

x86의 **TSO**(total store order)는 비교적 강한 메모리 모델입니다.
스토어 버퍼에서 생기는 대표적인 예외를 제외하면 메모리 순서를 많이 보존합니다.
그래서 x86에서는 `Acquire`/`Release`가 추가 실행 비용 없이 일반 load/store로 구현되는 경우가 많고,
주로 컴파일러 재배치를 막는 역할을 합니다.
반면 ARM과 RISC-V는 더 약한 모델이라 같은 보장을 만들기 위해 전용 명령어나 fence가 필요할 수 있습니다.

Rust의 `Ordering`은 바로 이 차이를 감추는 추상화입니다.
**어떤 CPU에서도 같은 의미의 순서 보장을 얻기 위해 작성하는 공통 언어**입니다.
x86에서 우연히 잘 동작한다는 이유로 `Relaxed`를 남용하면 ARM 계열 환경에서 문제가 드러날 수 있습니다.
반대로 Rust의 메모리 모델에 맞게 작성하면 컴파일러가 각 CPU에 필요한 명령을 선택합니다.

### 원자적 명령어는 어떻게 구현될까

`fetch_add`처럼 읽기와 쓰기를 한 번에 처리하는 RMW(read-modify-write) 연산도
아키텍처마다 구현 방식이 다릅니다.

x86에서는 명령어에 `lock` 접두사를 붙여 대상 캐시 라인에 대한 원자성을 보장합니다.
ARM에서는 전통적으로 **LL/SC**(load-linked/store-conditional), 즉
"읽은 뒤 누군가 값을 바꿨다면 쓰기에 실패하고 다시 시도한다"는 방식을 사용해 왔습니다.
최근 ARM은 여기에 LSE 같은 전용 원자적 명령어도 제공합니다.

x86에서는 `Relaxed`의 `fetch_add`와 `SeqCst`의 `fetch_add`가 같은 `lock` 계열 명령어로 컴파일되는 경우가 많습니다.
따라서 ordering을 약하게 바꿔도 RMW 자체의 비용이 줄지 않을 수 있습니다.
ARM에서는 ordering에 따라 실제 명령어 차이가 더 직접적으로 나타날 수 있습니다.

## 락과 원자적 연산 중 무엇을 쓸까

구조를 이해했으니 실제 선택으로 내려가 보겠습니다.
공유 카운터 하나를 `Mutex`로 보호하는 경우와 `AtomicU64`로 갱신하는 경우를 비교합니다.

<RustPlay code={lockVsAtomic} mode="release" title="공유 카운터: Mutex와 AtomicU64 비교" />

저자가 Playground의 2스레드 환경에서 측정했을 때 원자적 연산은 약 68밀리초,
`Mutex`는 약 270밀리초로 **약 4배 차이**가 났습니다.
`Mutex`를 사용할 때는 락 획득과 해제 자체에도 원자적 연산과 추가 제어 비용이 필요하기 때문입니다.
숫자 하나나 플래그 하나처럼 단순한 상태에서는 원자적 타입이 유리할 수 있다는 5장의 기준을 실제 수치로 확인한 셈입니다.

그렇다고 `Mutex`를 무조건 피해야 하는 것은 아닙니다.
경합이 거의 없으면 락의 빠른 경로도 매우 저렴하고,
복잡한 상태를 한 번에 안전하게 보호할 수 있다는 장점이 큽니다.
**먼저 `Mutex`로 정확하게 작성하고, 측정에서 실제 경합이 확인되면 최적화를 고민하는 것**이 좋은 순서입니다.

## 락프리의 기초 — CAS와 어려움

복잡한 자료구조를 락 없이 갱신할 때 핵심이 되는 연산이
**CAS**(compare-and-swap)입니다.
Rust에서는 `compare_exchange`를 사용합니다.
"현재 값이 예상한 값과 같다면 새 값으로 바꾸고, 다르면 실패한다"는 작업을 원자적으로 수행합니다.
전형적인 형태는 읽기 → 새 값 계산 → CAS → 실패하면 다시 시도하는 루프입니다.

고전적인 락프리 스택인 Treiber 스택의 `push`는 다음과 같은 뼈대를 가집니다.
생 포인터와 `unsafe`가 등장하며 정확한 안전 규칙은 [20장](/rust-deep/20-unsafe-ub/)에서 다룹니다.

```rust
// 개념을 보여 주기 위한 뼈대입니다. 아래에서 설명할 문제 때문에 이것만으로는 충분하지 않습니다
fn push(head: &AtomicPtr<Node>, new: *mut Node) {
    loop {
        let old = head.load(Ordering::Relaxed);
        unsafe { (*new).next = old; }
        // head가 아직 old라면 new로 바꿉니다
        if head.compare_exchange(old, new,
            Ordering::Release, Ordering::Relaxed).is_ok() {
            break;
        }
        // 다른 스레드가 먼저 바꿨다면 다시 읽고 시도합니다
    }
}
```

하지만 진짜 어려움은 여기서 시작됩니다.

- **ABA 문제** — `pop` 도중 다른 스레드가 A를 제거하고 다른 값을 넣었다가,
  메모리 재사용 때문에 다시 같은 주소 A가 head가 되면 값은 A→B→A로 바뀌었는데도 CAS는 "변하지 않았다"고 판단할 수 있습니다.
  포인터에 버전 번호를 함께 저장하는 태그 포인터 방식이 고전적인 대책입니다
- **메모리 회수 문제** — `pop`한 노드를 언제 해제해도 될까요?
  다른 스레드가 아직 그 포인터를 읽고 있을 수 있습니다.
  락이 없으므로 "아무도 더 이상 보지 않는다"는 사실을 보장하기 어렵습니다.
  대표적인 해결책이 **에포크 기반 회수**(epoch-based reclamation)입니다.
  모든 스레드가 특정 시점을 통과한 뒤 그 이전에 제거된 메모리를 안전하게 해제하는 방식입니다

Rust에서는 이런 구현이 대부분 `unsafe` 영역에 들어갑니다([20장](/rust-deep/20-unsafe-ub/)).
실무에서는 직접 구현하지 않는 것이 일반적인 선택입니다.
[crossbeam](https://github.com/crossbeam-rs/crossbeam)은 `crossbeam-epoch`을 비롯해
락프리 큐와 채널 같은 검증된 구현을 제공합니다.
락프리 구조를 직접 만드는 것은 측정에서 락 경합이 실제 병목으로 확인되고,
기존 라이브러리로도 해결되지 않을 때 고려할 마지막 수단에 가깝습니다.

## 정리

- 메모리 쓰기는 스토어 버퍼를 거칠 수 있습니다. 이 때문에 x86에서도 스토어→로드 순서가 뒤집혀 보일 수 있으며 실험에서는 20만 번 중 약 1.3만 번 관측됐습니다
- CPU마다 하드웨어 메모리 모델의 강도가 다릅니다. Rust의 `Ordering`은 이런 차이를 감추면서 이식 가능한 순서 보장을 표현하는 추상화입니다
- 공유 카운터 실험에서는 원자적 연산이 `Mutex`보다 약 4배 빨랐습니다. 하지만 기본 설계는 먼저 `Mutex`로 정확하게 작성한 뒤 측정으로 결정하는 편이 좋습니다
- 락프리 구조의 핵심은 CAS 재시도 루프지만 ABA 문제와 메모리 회수라는 어려움이 있습니다. 실무에서는 crossbeam 같은 검증된 구현을 우선 사용합니다
