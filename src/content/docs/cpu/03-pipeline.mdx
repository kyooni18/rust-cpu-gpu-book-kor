- 파이프라인: CPU가 여러 명령어의 처리 단계를 겹쳐 실행하는 원리

- 분기 예측 실패의 비용을 실제로 측정하고, 데이터 순서만으로 10배 차이가 나는 이유

## 명령어 처리를 겹쳐 실행하기

1장에서는 CPU가 명령어를 "페치 → 디코드 → 실행" 순서로 처리한다고
설명했습니다. 하지만 명령어 하나가 끝난 다음에야 다음 명령어를 시작하는 것은 아닙니다.
그렇게 하면 각 단계의 회로가 대부분의 시간 동안 아무 일도 하지 않고 기다리게 됩니다.

그래서 CPU는 명령어 처리 단계를 **파이프라인**(pipeline)으로 겹칩니다.
예를 들어 공장의 조립 라인을 생각할 수 있습니다. 공정을 여러 단계로 나누고,
첫 번째 제품이 두 번째 공정으로 이동하면 곧바로 두 번째 제품을 첫 번째 공정에 넣는 방식입니다.

그림은 교과서에서 자주 사용하는 5단계 파이프라인의 예입니다.
명령어 하나가 완료되기까지는 5사이클이 필요하지만, 파이프라인이 모두 차 있으면
**매 사이클마다 명령어 하나가 완료됩니다**.
실제 현대 CPU의 파이프라인은 더 잘게 나뉘어 있으며 약 15~20단계 정도인 경우가 많습니다.

## 파이프라인을 멈추게 하는 것

조립 라인에서는 중간 단계가 멈추면 전체 흐름에도 영향을 줍니다.
파이프라인의 진행을 방해하는 요인을 **해저드**(hazard),
그 때문에 생기는 대기를 **스톨**(stall)이라고 부릅니다.
주요 해저드는 두 종류입니다.

- **데이터 해저드**(data hazard) — 앞 명령어의 결과를 다음 명령어가 사용한다면
  결과가 나올 때까지 기다려야 합니다. 앞 장의 포인터 체이싱이 느렸던 이유도
  "다음에 읽을 위치"가 "현재 읽기의 결과"에 의존한다는 점에서
  데이터 해저드의 극단적인 사례라고 볼 수 있습니다
- **제어 해저드**(control hazard) — `if`나 루프는 기계어 수준에서는 조건부 점프 명령어입니다.
  점프할지 말지가 확정될 때까지는 다음에 어떤 명령어를 페치해야 할지 알 수 없습니다

이 중 제어 해저드는 특히 큰 영향을 줍니다. 프로그램에서는 대략
5~6개 명령어마다 한 번꼴로 분기가 나타납니다. 분기 때마다
파이프라인을 멈춘다면 성능이 크게 떨어집니다.

## 분기 예측 — 결과를 기다리지 않고 먼저 실행하기

그래서 CPU는 **분기 예측기**(branch predictor)라는 회로를 이용해
"이 분기는 아마 이쪽으로 갈 것"이라고 예측합니다. 결과가 확정되기를 기다리지 않고
예측한 경로의 명령어를 먼저 실행합니다.
이 방식을 **추측 실행**(speculative execution)이라고 부릅니다.

- 예측이 맞으면 분기에 따른 비용은 거의 없습니다
- 예측이 틀리면 미리 실행한 결과를 모두 버리고 올바른 경로를 다시 실행합니다.
  이때 대략 15~25사이클 정도의 페널티가 생깁니다

현대의 분기 예측기는 과거 분기 기록을 이용해 패턴을 학습하며 정확도가 매우 높습니다.
루프 종료 조건은 거의 항상 맞히고, 규칙적인 패턴도 잘 학습합니다.
예측하기 어려운 것은 규칙성이 없는 동전 던지기 같은 분기입니다.

## 실험: 분기 예측 실패를 확인하기

의도적으로 "동전 던지기 같은 분기"를 만들어 비용을 측정해 보겠습니다.
0~255 범위의 난수 1,000만 개에서 "128 이상이면 합계에 더한다"는 처리만 수행합니다.
같은 데이터를 사용하면서 **배열의 순서만** 바꿔 두 번 실행합니다.

<RustPlay code={branch} mode="release" title="같은 코드·같은 데이터, 다른 것은 순서뿐" />

저자가 Playground에서 측정했을 때 정렬하지 않은 데이터는 약 42밀리초,
정렬한 데이터는 약 4밀리초였습니다. **데이터 순서만 바꿨는데 약 10배 차이**가 났습니다.

- 정렬하지 않은 경우 `v >= 128`의 참과 거짓이 원소마다 무작위로 바뀝니다.
  예측기가 학습할 패턴이 없으므로 분기의 약 절반을 잘못 예측합니다.
  1,000만 번의 절반인 약 500만 번의 실패에 각각 20사이클 안팎의 페널티가 더해집니다
- 정렬한 경우 앞부분은 계속 거짓이고 뒷부분은 계속 참입니다.
  값이 바뀌는 한 지점을 제외하면 거의 모든 분기를 올바르게 예측할 수 있습니다

계산 복잡도만 보면 두 경우 모두 O(n)으로 같습니다. 하지만 실행 시간은
약 10배 차이가 납니다. CPU의 실제 동작을 이해해야 이런 차이를 설명할 수 있습니다.

소스 코드의 `if`가 실제 분기 명령어로 남는지는 컴파일러가 결정합니다.
이 실험에서는 실제 측정 결과로 보아 분기로 남아 있지만,
컴파일러 버전이 바뀌면 결과도 달라질 수 있습니다.
이 실험의 핵심은 "예측할 수 없는 분기는 비용이 크다"는 원리를 확인하는 것입니다.

## 분기 없애기

예측할 수 없는 분기가 비싸다면 분기 자체를 없애는 방법도 있습니다.
이를 **브랜치리스**(branchless) 코드라고 부릅니다.

대표적인 방법은 조건을 `0`이나 `1` 같은 수치로 바꿔 산술 연산에 포함하는 것입니다.
`if`가 사라지고 항상 같은 명령어열을 실행하게 됩니다.
같은 처리를 이터레이터로 작성한 경우도 함께 측정해 보겠습니다.

<RustPlay code={branchless} mode="release" title="분기를 없앤 두 가지 작성법" />

저자가 Playground에서 측정했을 때 산술 연산 버전과 이터레이터 버전 모두
정렬 여부와 관계없이 **약 3.6밀리초**였습니다. 데이터 순서에 따른 차이가 사라졌고,
정렬하지 않은 데이터에서는 원래 코드보다 10배 이상 빨라졌습니다.

이터레이터 버전도 빠르다는 점은 눈여겨볼 만합니다. `filter().map().sum()`이라는
형태는 컴파일러가 "모든 원소에 같은 계산을 적용한다"는 구조를 파악하기 쉽습니다.
따라서 분기가 없는 명령어열, 경우에 따라서는 SIMD 명령어로도 변환하기 쉽습니다.
조건 분기를 **조건부 이동**(conditional move) 명령어 같은 계산으로 바꾸는
컴파일러 최적화를 **if 변환**(if-conversion)이라고 부릅니다.
첫 번째 실험의 `if`는 if 변환되지 않고 실제 분기 명령어로 실행되었습니다.
같은 의미의 코드라도 작성 방식에 따라 컴파일러가 분기를 없앨 수도 있고
그렇지 못할 수도 있다는 뜻입니다([7장](/rust-opt/07-zero-cost/)에서 다시 살펴봅니다).

다만 브랜치리스 코드가 항상 더 빠른 것은 아닙니다.
조건의 양쪽 계산을 항상 수행해야 할 수도 있기 때문입니다.
예측이 매우 잘 맞는 분기(거의 항상 참인 경우 등)는 `if`를 그대로 두는 편이 더 빠를 때도 많습니다.
어떤 방식이 좋은지는 측정해서 판단해야 합니다([8장](/rust-opt/08-measure/)).

:::note[추측 실행과 취약점]
추측 실행은 예측이 틀리면 결과를 버리는 방식으로 프로그램의 논리적 정확성을 유지합니다.
하지만 버려진 실행이 캐시에 남긴 흔적을 악용하는 공격이
2018년에 공개된 Spectre와 Meltdown입니다. 하드웨어 성능 최적화가
보안에 영향을 줄 수 있다는 대표적인 사례입니다.
:::

## 한 사이클에 여러 명령어 실행하기 — 슈퍼스칼라

파이프라인을 사용하면 "매 사이클마다 명령어 하나"를 완료할 수 있게 됩니다.
현대 CPU는 여기서 더 나아가 여러 실행 유닛을 두고
**한 사이클에 약 4~8개 명령어**를 동시에 처리할 수 있습니다.
이를 **슈퍼스칼라**(superscalar) 실행이라고 부릅니다.

또한 명령어를 프로그램에 적힌 순서대로만 실행하지 않습니다.
의존 관계가 해결된 명령어부터 먼저 실행하는 **비순차 실행**(out-of-order execution)도 사용합니다.
명령어 사이에 숨어 있는 "동시에 실행할 수 있는 정도"를
**명령어 수준 병렬성**(instruction-level parallelism, ILP)이라고 부르고,
한 사이클에 실제로 실행하는 명령어 수를 **IPC**(instructions per cycle)라고 부릅니다.

이 구조를 얼마나 잘 활용할 수 있는지는 **명령어 사이의 의존 관계**가 결정합니다.
실험으로 확인해 보겠습니다. 부동소수점 값의 합계를 구할 때
"변수 하나에 계속 더하는 경우"와 "변수 네 개에 나눠서 더하는 경우"를 비교합니다.

<RustPlay code={ilp} mode="release" title="의존성 연결을 네 갈래로 나누기" />

코드를 조금 설명하면 `chunks_exact(4)`는 슬라이스를 네 원소씩 묶어
순회하는 이터레이터입니다. 네 개로 나누어떨어지지 않고 남은 원소는 `remainder()`로
꺼내 별도로 처리합니다.

저자가 Playground에서 측정했을 때 각각 약 19밀리초와 약 5밀리초로,
**약 3.8배의 차이**가 났습니다.

변수 하나만 사용하는 경우 `sum += v`는 바로 앞 덧셈 결과에 의존합니다.
따라서 부동소수점 덧셈의 지연 시간인 3~4사이클마다 하나씩만 진행할 수 있습니다.
CPU에 실행 유닛이 여러 개 있어도 의존성이 하나의 직렬 연결로 이어지면 동시에 사용할 수 없습니다.

변수를 네 개로 나누면 서로 독립적인 의존성 연결이 네 개가 되고,
여러 덧셈을 동시에 진행할 수 있습니다.

정수 합계에서는 컴파일러가 이런 변환을 자동으로 적용하는 경우가 많습니다.
하지만 부동소수점은 덧셈 순서를 바꾸면 결과가 조금 달라질 수 있으므로
컴파일러가 임의로 순서를 바꾸지 않습니다. 이 내용은 다음 장에서 더 자세히 다룹니다.

## 정리

- CPU는 명령어를 파이프라인으로 겹쳐 처리하고, 슈퍼스칼라와 비순차 실행을 이용해
  한 사이클에 여러 명령어를 실행합니다
- 분기는 미리 예측해 추측 실행합니다. 예측 실패는 약 15~25사이클의 손실을 만들며,
  예측하기 어려운 분기는 데이터 순서만으로 약 10배의 차이를 만들 수 있습니다
- 예측하기 어려운 분기는 산술 연산이나 이터레이터를 이용해 브랜치리스 형태로 바꿀 수 있습니다.
  하지만 항상 더 빠른 것은 아니므로 측정해서 판단해야 합니다
- 성능을 결정하는 것은 명령어 수뿐만 아니라 명령어 사이의 의존 관계입니다.
  서로 독립적인 계산 흐름을 늘리면 IPC를 높일 수 있습니다

"모든 원소에 같은 계산을 적용하는" 작업은 분기를 없앨 수 있을 뿐 아니라,
여러 원소를 하나의 명령어로 한꺼번에 계산할 수도 있습니다.
다음 장에서는 그 원리인 SIMD를 살펴봅니다.
