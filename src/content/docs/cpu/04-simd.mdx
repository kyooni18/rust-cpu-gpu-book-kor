- SIMD: 하나의 명령어로 여러 데이터를 동시에 계산하는 방식

## 하나의 명령어로 여러 데이터 처리 — SIMD

앞 장까지 살펴본 CPU에서는 하나의 덧셈 명령어가 한 쌍의 숫자를 더했습니다.
하지만 배열의 모든 원소에 같은 계산을 적용하는 작업에서는
같은 명령어를 계속 반복하게 됩니다.
그렇다면 **하나의 명령어로 여러 원소를 한꺼번에 계산**하는 편이 더 효율적입니다.

이 방식을 **SIMD**(single instruction, multiple data)라고 부릅니다.
SIMD 명령어는 일반 레지스터보다 폭이 넓은 **벡터 레지스터**(vector register)를 사용합니다.
예를 들어 128비트 벡터 레지스터에는 32비트 정수(`i32`) 네 개가 들어갑니다.
이렇게 벡터 안에서 개별 원소가 차지하는 구역을 **레인**(lane)이라고 부릅니다.
다음 그림은 스칼라 방식과 SIMD 방식의 차이를 보여 줍니다.

SIMD 명령어는 CPU 세대가 발전하면서 계속 확장되어 왔습니다.
대략 다음 계열을 알고 있으면 충분합니다.

- x86-64 — **SSE2**(128비트, 모든 x86-64 CPU에서 지원),
  **AVX/AVX2**(256비트), **AVX-512**(512비트, 일부 CPU에서만 지원)
- ARM64 — **NEON**(128비트, 모든 ARM64 CPU에서 지원), SVE(가변 길이, 일부 CPU에서 지원)

컴파일러는 기본적으로 해당 아키텍처의 모든 CPU가 지원하는 명령어만 사용합니다.
x86-64에서는 SSE2, ARM64에서는 NEON이 기준입니다.

## 자동 벡터화 — 컴파일러가 SIMD를 사용합니다

SIMD를 사용하기 위해 항상 특별한 코드를 작성해야 하는 것은 아닙니다.
컴파일러, 정확히는 LLVM([6장](/rust-opt/06-compiler/))은 루프를 분석해
SIMD 명령어를 사용하는 코드로 바꾸는 **자동 벡터화**(auto-vectorization)를 수행합니다.

1장과 같은 방법으로 `i32` 슬라이스를 합산하는 함수의 어셈블리를 확인해 보겠습니다.

```rust
pub fn sum(v: &[i32]) -> i32 {
    let mut s = 0i32;
    for &x in v {
        s = s.wrapping_add(x);
    }
    s
}
```

release 빌드에서는 루프의 핵심 부분이 다음처럼 바뀝니다(x86-64 일부 발췌).

```asm
.LBB0_5:
	movdqu	xmm2, xmmword ptr [rdi + 4*rax]
	paddd	xmm1, xmm2
	movdqu	xmm2, xmmword ptr [rdi + 4*rax + 16]
	paddd	xmm0, xmm2
	add	rax, 8
	cmp	r8, rax
	jne	.LBB0_5
```

`xmm0`~`xmm2`는 128비트 벡터 레지스터이고, `paddd`는
`i32` 네 레인을 동시에 더하는 명령어입니다.
또한 `xmm0`과 `xmm1`이라는 **두 개의 누산기**를 사용합니다.
앞 장에서 직접 작성했던 "의존 체인을 여러 개로 나누기"를 컴파일러가 자동으로 적용해
루프 한 번에 여덟 원소를 처리하는 셈입니다.

자동 벡터화는 대체로 다음 조건을 만족할 때 잘 적용됩니다.

- 연속된 메모리를 순서대로 읽고 씁니다. 슬라이스와 `Vec` 순회가 대표적입니다.
  비연속 접근을 지원하는 SIMD 명령어도 있지만 연속 접근이 가장 효율적입니다
- 반복 사이의 의존성이 없습니다. 이전 반복의 결과를 다음 반복이 필요로 하지 않는 형태입니다.
  합계는 겉으로 보면 의존성이 있지만, 정수처럼 순서를 바꿔도 결과가 같다면 여러 부분 합계로 나눌 수 있습니다
- 분기가 없거나, 앞 장에서 살펴본 if 변환으로 분기를 없앨 수 있는 형태입니다

2장에서 SoA가 유리했던 이유도 여기와 연결됩니다.
필요한 데이터가 메모리에 연속해서 놓인다는 것은 캐시뿐 아니라 SIMD에도 좋은 조건입니다.

## 실험: 정수는 빠른데 부동소수점은 느립니다

같은 형태의 합계 루프를 `i32`와 `f32`로 실행해 보겠습니다.

<RustPlay code={auto} mode="release" title="같은 형태의 합계: i32와 f32 비교" />

저자가 Playground에서 측정했을 때 `i32`는 약 1.5밀리초,
`f32`는 약 18.6밀리초였습니다. **약 12배 차이**입니다.
`i32`는 앞에서 본 것처럼 SIMD로 벡터화되지만,
`f32`는 원소를 하나씩 순서대로 더하는 코드로 남기 때문입니다.

왜 컴파일러는 `f32` 합계를 자동으로 벡터화하지 않을까요?

부동소수점 덧셈은 수학의 실수와 달리 **결합법칙이 성립하지 않습니다**.
유한한 비트 수로 매 연산 결과를 반올림하기 때문에
`(a + b) + c`와 `a + (b + c)`의 결과가 조금 달라질 수 있습니다.
SIMD 벡터화나 여러 누산기로 나누는 방식은 덧셈 순서를 바꾸므로
**결과의 비트 패턴이 달라질 수 있습니다**.
Rust 컴파일러는 기본적으로 작성된 연산 순서가 만드는 결과를 보존하기 때문에
이런 재배치를 임의로 적용하지 않습니다.

실험 출력에서도 `i32` 버전과 `f32` 버전의 합계 자체가 다릅니다.
983,644,560과 990,000,000처럼 차이가 나타나는 것은
`f32`를 순차적으로 더하는 동안 반올림 오차가 누적되었기 때문입니다.
즉 "연산 순서가 결과를 바꿀 수 있다"는 사실을 직접 확인할 수 있습니다.

:::note[fast-math]
C/C++ 컴파일러에는 부동소수점 재배치를 허용하는 `-ffast-math` 옵션이 있습니다.
Rust 안정판에는 이에 해당하는 전역 스위치가 없고,
연산 단위의 `fadd_fast` 같은 기능이 nightly에 존재합니다(2026년 기준).
정밀도와 의미론을 바꾸는 최적화는 프로그래머가 명시적으로 선택해야 한다는 방향입니다.
:::

## 명시적 SIMD — portable SIMD

그렇다면 `f32` 합계를 빠르게 만들고 싶을 때는 어떻게 할까요?
"연산 순서를 바꿔도 된다"는 판단을 프로그래머가 직접 내리고 SIMD를 명시적으로 사용할 수 있습니다.

nightly Rust에는 **portable SIMD**(`std::simd`)라는 CPU 종류에 독립적인 SIMD API가 있습니다.
`f32x8`은 `f32` 여덟 개의 레인을 가진 벡터 타입입니다.
다음 코드는 nightly Playground에서 실행됩니다.

<RustPlay code={nightlySimd} mode="release" channel="nightly" title="f32 합계를 8개 레인으로 계산하기(nightly)" />

저자의 Playground 실측에서는 스칼라 버전 약 18.5밀리초,
SIMD 버전 약 2.4밀리초로 **약 8배 차이**가 났습니다.
또 SIMD 버전의 합계는 990,000,000으로 정확한 값에 더 가깝게 나옵니다.
여덟 개의 부분 합계가 각각 더 작은 값을 유지하기 때문에 반올림 오차도 줄어든 것입니다.
즉 단순히 정밀도를 희생해 속도를 얻은 것이 아니라,
덧셈 순서를 어떻게 구성할지 프로그래머가 직접 결정한 결과입니다.

코드에 등장하는 함수도 간단히 정리해 보겠습니다.
`splat`은 모든 레인을 같은 값으로 채우고,
`from_slice`는 슬라이스 앞의 여덟 원소를 레인에 읽어 들이며,
`reduce_sum`은 여덟 레인을 하나의 합계로 줄입니다.
`f32x8`의 여덟 레인은 논리적인 폭입니다.
실제 하드웨어에서 어떤 폭의 명령어를 사용할지는 컴파일 대상 CPU에 따라 달라집니다.
기본 x86-64의 SSE2만 허용된 환경에서는 128비트 명령어 여러 개로 나뉠 수 있습니다.

## 안정판의 명시적 SIMD — std::arch

`std::simd`는 2026년 기준 아직 nightly 기능입니다.
안정판에서 SIMD를 명시적으로 사용하려면 `std::arch`의
CPU 명령어에 직접 대응하는 **인트린식**(intrinsic)을 사용할 수 있습니다.

```rust
#[cfg(target_arch = "x86_64")]
fn sum_f32(v: &[f32]) -> f32 {
    if is_x86_feature_detected!("avx2") {
        // AVX2를 지원하는 CPU에서만 AVX2 구현을 호출합니다
        unsafe { sum_f32_avx2(v) }
    } else {
        v.iter().sum()
    }
}
```

인트린식은 특정 CPU 명령어와 직접 연결되므로 이식성이 떨어지고 `unsafe`가 필요합니다.
지원하지 않는 CPU에서 해당 명령어를 실행하면 올바른 동작을 보장할 수 없기 때문입니다.
따라서 AVX2 구현 함수에는 `#[target_feature(enable = "avx2")]`를 붙이고,
실행 중 CPU 지원 여부를 확인하는 `is_x86_feature_detected!` 같은
**실행 시 기능 검출**(runtime feature detection)로 보호하는 형태가 일반적입니다.

이 책에서는 더 깊게 들어가지 않습니다.
안정판에서 마지막 수단으로 사용할 수 있다는 점 정도만 알아두면 충분합니다.
실무에서는 `wide` 같은 크레이트를 사용하거나 자동 벡터화가 잘 적용되는 형태로 루프를 만드는 편이 더 현실적인 경우가 많습니다.

## 더 새로운 SIMD 명령어를 컴파일러에 허용하기

자동 벡터화 성능은 컴파일러에 어떤 CPU 명령어까지 사용할 수 있는지 알려 주는 것만으로도 달라질 수 있습니다.
기본 x86-64에서는 SSE2가 기준이지만 다음 옵션으로 AVX2 같은 더 새로운 확장을 허용할 수 있습니다.

```sh
# 현재 머신이 지원하는 모든 명령어를 허용합니다. 이 머신 전용 바이너리가 됩니다
RUSTFLAGS="-C target-cpu=native" cargo build --release

# 특정 확장만 허용합니다
RUSTFLAGS="-C target-feature=+avx2" cargo build --release
```

배포할 때는 주의해야 합니다.
AVX2를 사용하도록 컴파일한 바이너리를 AVX2가 없는 CPU에서 실행해서는 안 됩니다.
로컬에서만 실행하는 계산 프로그램이라면 `target-cpu=native`가 간단한 선택이지만,
여러 CPU에 배포하는 프로그램에서는 기본 타깃을 유지하거나 실행 시 기능 검출로 구현을 선택해야 합니다.

## 정리

- SIMD는 하나의 명령어로 여러 레인을 동시에 계산합니다.
  x86-64에서는 SSE2(128비트)가 기본이고 AVX2 이후 확장은 명시적으로 허용해야 할 수 있습니다
- 컴파일러는 연속 접근, 반복 사이 의존성 없음, 단순한 제어 흐름 같은 조건을 만족하는 루프를 자동 벡터화합니다.
  2장의 연속적인 데이터 배치는 SIMD에도 중요합니다
- 부동소수점 덧셈은 결합법칙이 성립하지 않으므로 연산 순서를 바꾸는 벡터화를 컴파일러가 기본적으로 적용하지 않습니다.
  실험에서는 같은 형태의 합계가 12배 차이 났습니다
- `portable_simd`(nightly)를 사용하면 명시적인 SIMD를 비교적 이식성 있게 작성할 수 있습니다.
  부분 합계를 사용하면서 오히려 수치 오차가 줄어들 수도 있습니다

여기까지는 하나의 CPU 코어 내부에서 성능을 높이는 방법을 살펴봤습니다.
현대 CPU에는 여러 개의 코어가 있습니다.
다음 장에서는 여러 코어를 사용하는 병렬 처리와,
코어 사이에서 메모리를 공유할 때 생기는 문제를 살펴봅니다.
