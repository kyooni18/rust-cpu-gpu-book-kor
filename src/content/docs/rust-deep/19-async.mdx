이 장에서 알 수 있는 것:

- `async fn`이 컴파일되면 무엇이 되는지 — 상태 머신과 실제 크기
- `poll`과 `Waker`를 이용한 구동 모델, 그리고 tokio 런타임이 하는 일
- 태스크와 OS 스레드의 비용 차이(생성 비용 기준 약 160배)
- async의 가장 큰 함정 — 런타임을 블로킹하는 코드와 그 실제 영향
- 왜 이 내용이 필요한가 — 웹 애플리케이션의 동시성에서 async는 핵심 도구입니다.
  [5장](/cpu/05-multicore/)에서 "동시성은 async의 영역"이라고 구분했으므로,
  내부 구조까지 보지 않으면 병렬성과 동시성의 지도가 완성되지 않습니다

## async fn은 무엇으로 컴파일될까

가장 중요한 사실부터 시작하겠습니다. **`async fn`은 호출만 해서는 실행되지 않습니다**.
[8장](/rust-opt/08-measure/)에서 본 지연 평가 이터레이터처럼,
`async fn` 호출은 "앞으로 실행할 작업의 계획"을 만들어 반환할 뿐입니다.
이 계획이 `Future`입니다.

그렇다면 `Future`의 실체는 무엇일까요? 컴파일러는 `async fn` 본문을
**`.await` 위치마다 나뉜 상태 머신**(state machine)으로 변환합니다.
`enum`으로 비유하면 "시작 전", "첫 번째 await에서 중단", "두 번째 await에서 중단" 같은
상태를 가지며, 뒤에서 설명할 `poll`이 호출될 때마다 이어서 실행하고 다음 상태로 이동합니다.

여기서 크기가 매우 중요합니다. **중단된 동안 살아 있어야 하는 지역 변수는
모두 이 상태 머신 안에 저장됩니다**. 직접 확인해 보겠습니다.

<RustPlay code={futureSize} mode="release" title="Future의 크기는 무엇으로 결정될까?" />

저자가 Playground에서 측정한 결과는 다음과 같습니다.

- 아무 데이터도 들고 있지 않은 `async fn`의 Future: **1바이트**(상태 번호 정도)
- 4KB 배열을 `.await` 너머까지 유지하는 Future: **4120바이트**
- 같은 배열이지만 `.await` 전에 사용을 끝낸 Future: **32바이트**

`.await`를 가로질러 살아 있는 변수는 Future 안에 포함됩니다.
이 규칙을 모르면 큰 버퍼를 들고 `await`하는 함수가 겹치면서 Future 크기가 크게 늘어날 수 있습니다.
중첩된 `async fn`의 Future는 바깥 Future 안에 다시 포함되므로 깊은 호출 구조에서는 크기가 합쳐집니다.
tokio의 `spawn`은 Future를 힙에 올리므로 이 크기는
[18장](/rust-deep/18-allocators/)에서 다룬 할당 비용과도 직접 연결됩니다.
대책은 실험의 세 번째 경우가 보여 줍니다. **큰 임시 데이터는 await 전에 놓아주거나,
필요하다면 `Box`로 분리하는 편이 좋습니다**.

## poll, Waker, 런타임

계획서인 Future를 실제로 실행시키는 주체가 **비동기 런타임**(async runtime)입니다.
Rust 언어는 Future의 형태만 정의하고, 실행 방법은 tokio 같은 라이브러리에 맡깁니다.
그 형태가 `Future` 트레이트입니다.

```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

`Pin<&mut Self>`는 "이 Future를 이제 메모리에서 이동시키지 않는다"는 약속입니다.
상태 머신 내부에는 자기 자신의 다른 필드를 가리키는 참조가 생길 수 있습니다.
예를 들어 `.await`를 가로질러 지역 변수의 참조가 살아 있을 수 있습니다.
이때 구조체 전체가 이동하면 내부 참조가 깨질 수 있으므로 `Pin`이 이동을 금지합니다.
`Context`에는 뒤에서 설명할 Waker가 들어 있습니다.

구동 방식은 다음과 같은 풀(pull) 모델입니다.

1. 런타임이 Future의 `poll`을 호출합니다 — "진행할 수 있는 만큼 진행해 주세요"
2. Future는 실행 가능한 부분까지 실행한 뒤 끝났다면 `Ready(결과)`, 기다려야 한다면 `Pending`을 반환합니다.
   이때 소켓 같은 대기 대상이 준비되면 다시 깨워 달라고 **Waker**라는 알림 핸들을 등록합니다
3. Linux의 epoll 같은 OS I/O 알림이 오면 런타임은 Waker를 통해 해당 태스크를 실행 대기열에 다시 넣고 `poll`을 호출합니다

즉 async 동시성은 **수많은 상태 머신을 소수의 OS 스레드가 번갈아 `poll`하는 구조**입니다.
tokio의 기본 멀티스레드 런타임은 보통 코어 수에 맞춘 워커 스레드를 만들고,
[5장](/cpu/05-multicore/)의 Rayon과 비슷한 **워크 스틸링**으로 태스크를 나눕니다.
차이는 작업의 성격입니다. Rayon은 "계산을 끝낼 때까지 실행하는 작업"에 맞춰져 있고,
tokio는 "조금 실행한 뒤 곧 `Pending`으로 돌아오는 작업"을 효율적으로 다루도록 설계되어 있습니다.

## 태스크는 무엇이 가벼울까 — 실측

"async 태스크는 OS 스레드보다 가볍다"고 자주 말합니다. 실제 숫자로 비교해 보겠습니다.

<RustPlay code={spawnCost} mode="release" title="OS 스레드 1만 개와 tokio 태스크 10만 개" />

저자가 Playground에서 측정했을 때 OS 스레드 1만 개를 생성하고 합류시키는 데 약 760밀리초,
스레드 하나당 약 76마이크로초가 걸렸습니다.
tokio 태스크 10만 개는 약 47밀리초, 태스크 하나당 약 0.5마이크로초였습니다.
**하나당 약 160배 차이**입니다.
규모와 조건이 완전히 같은 비교는 아니지만, 스레드 10만 개를 만드는 실험 자체가 비현실적이라는 점도
둘의 구조적 차이를 보여 줍니다.

차이가 생기는 이유는 분명합니다. OS 스레드는 커널 시스템 콜
([27장](/systems/27-os-layer/))이 필요하고, 스택을 위한 메모리 공간도 준비해야 합니다.
스택은 보통 수 MB의 가상 주소 공간을 예약하고 실제 물리 메모리는
[14장](/cpu-deep/14-virtual-memory/)의 디맨드 페이징으로 필요할 때 붙습니다.
반면 tokio 태스크는 사용자 공간에서 Future 크기만큼 힙 할당을 하고
대기열에 넣는 정도입니다. "연결 하나당 태스크 하나"를 수만~수십만 개까지 만들 수 있는 이유입니다.

태스크 전환도 같은 맥락입니다. 한 태스크가 `Pending`을 반환하고 다른 태스크를 `poll`하는 과정은
사용자 공간의 함수 호출과 큐 조작에 가깝습니다.
OS 컨텍스트 스위치보다 훨씬 가볍습니다. 27장에서 실제 수치를 비교합니다.

## 가장 큰 함정 — 런타임을 블로킹하기

async의 협력적 실행 모델에는 중요한 전제가 있습니다.
**태스크는 `poll`된 뒤 가능한 빨리 `Pending`이나 `Ready`를 반환해야 합니다**.
`poll` 내부에서 오랫동안 돌아오지 않는 태스크는 워커 스레드 하나를 독점하고,
같은 워커에서 실행될 다른 태스크들까지 모두 지연시킵니다.

직접 측정해 보겠습니다. 워커가 하나뿐인 런타임에 두 태스크를 넣습니다.
태스크 A는 300밀리초 동안 동기적으로 잠들어 CPU를 돌려주지 않고,
태스크 B는 50밀리초 타이머 뒤에 끝나야 합니다.

<RustPlay code={blocking} mode="release" title="블로킹 코드가 비동기 런타임을 멈춘다" />

저자가 Playground에서 측정했을 때 태스크 B는 **약 300밀리초 뒤**에 완료됐습니다.
자신의 타이머는 50밀리초였지만, 태스크 A가 워커를 돌려주지 않는 동안 한 번도 `poll`되지 못했습니다.
A를 tokio의 `spawn_blocking`으로 옮기면 B는 예정대로 약 51밀리초에 끝납니다.
`spawn_blocking`은 블로킹 작업을 별도의 스레드 풀로 보내는 API입니다.

실무에서는 다음 원칙이 중요합니다.

- **동기 I/O, 무거운 CPU 계산, 오래 기다리는 락을 async 태스크 안에서 직접 실행하지 않습니다.**
  `spawn_blocking`으로 격리하거나, 계산 중심 작업은 Rayon으로 넘깁니다
- 멀티스레드 런타임이라고 문제가 사라지지는 않습니다. 워커가 8개라면 블로킹 작업 8개만으로 전체 워커가 막힐 수 있습니다.
  부하가 높아졌을 때만 지연 시간이 튀는 형태라 발견하기도 어렵습니다
- "무거운 poll"의 정확한 경계는 작업과 환경에 따라 다르지만, tokio 관련 설명에서는 대략 10~100마이크로초 이상 워커를 독점하는 작업을 주의하라고 자주 권합니다

:::note[.await와 제로 비용 추상화]
상태 머신으로 변환되는 과정 자체는 [7장](/rust-opt/07-zero-cost/)의 의미에서 제로 비용에 가깝습니다.
`.await` 한 번의 기본 비용은 함수 호출과 분기 정도입니다.
실제 비용은 Future 크기, 태스크를 `spawn`할 때의 힙 할당,
런타임의 I/O 다중화 구조에서 생깁니다.
"async라서 느리다"가 아니라 "어느 층의 비용인가"를 구분해서 보는 편이 정확합니다.
:::

## 사용 기준 — async / 스레드 / Rayon

[5장](/cpu/05-multicore/)의 지도를 완성해 보겠습니다.

| 도구 | 잘 맞는 작업 | 단위 비용 |
| --- | --- | --- |
| **async (tokio)** | 많은 I/O 대기를 동시에 처리 | 태스크 약 0.5µs, 대기 자체는 매우 저렴 |
| **OS 스레드** | 소수의 오래 살아 있는 동시 작업, 블로킹 작업 격리 | 생성 약 76µs + 스택 |
| **Rayon** | CPU를 최대한 사용하는 데이터 병렬 계산 | 5장 참고 |

웹 서버에서는 이 세 가지를 함께 사용하는 경우가 많습니다.
연결 수락과 I/O 대기는 tokio가 담당하고, 요청 중 발견된 무거운 계산은 Rayon이나 `spawn_blocking`으로 넘깁니다.
반대로 계산을 async 워커에서 직접 오래 실행하거나, I/O 대기를 Rayon에서 처리하면 각 도구의 장점을 잃습니다.

## 정리

- `async fn`은 `.await` 지점으로 나뉜 상태 머신을 반환합니다.
  await를 가로지르는 변수는 Future 안에 저장되며, 실험에서는 크기가 1바이트에서 4120바이트까지 달라졌습니다
- 런타임은 `poll`과 Waker로 상태 머신을 움직입니다. tokio는 여러 워커와 워크 스틸링으로 태스크를 분배합니다
- 태스크 생성은 OS 스레드 생성보다 하나당 약 160배 저렴했습니다. "연결 하나당 태스크 하나"가 가능한 이유입니다
- `poll`을 오래 점유하면 런타임 전체가 지연됩니다. 실험에서는 50ms 태스크가 약 300ms까지 밀렸습니다.
  동기 I/O와 무거운 계산은 `spawn_blocking`이나 Rayon으로 옮깁니다
- async, OS 스레드, Rayon은 경쟁 관계가 아니라 대기·장기 작업·계산이라는 서로 다른 역할을 담당합니다
