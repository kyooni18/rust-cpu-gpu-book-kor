- **정의되지 않은 동작**(undefined behavior, UB)의 정확한 의미와 왜 정말로 "무슨 일이 일어나도 이상하지 않은" 상태인지

  이 도구를 안전하게 다루는 법을 모르면 최적화 도구 상자가 완성되지 않습니다.
  또한 UB의 이해는 [6장](/rust-opt/06-compiler/)에서 다룬 컴파일러 최적화의 반대편을 이해하는 일이기도 합니다

## unsafe는 무엇을 해제할까

`unsafe` 블록을 "모든 검사가 꺼지는 모드"라고 생각하면 안 됩니다.
대표적으로 `unsafe`가 허용하는 것은 다음과 같은 작업입니다.

1. 원시 포인터(`*const T` / `*mut T`) 역참조
2. `unsafe fn` 호출(FFI 함수 포함)
3. 가변 static 또는 외부(extern) static 변수 접근
4. `unsafe trait`(`Send`/`Sync` 등) 구현
5. `union` 필드 읽기

에디션 2024에서는 `extern` 블록이나 일부 속성 선언 자체에 `unsafe`를 적는 경우가 생기는 등
언어가 발전하면서 세부 규칙은 조금씩 늘어납니다. 정확한 목록은 Rust 언어 레퍼런스를 참고해야 합니다.

중요한 점은 빌림 검사와 타입 검사가 `unsafe` 안에서도 그대로 작동한다는 것입니다.
`unsafe`의 의미는 "검사를 포기한다"가 아니라,
**"컴파일러가 증명할 수 없는 안전 조건을 내가 직접 증명했다"고 서명하는 것**에 가깝습니다.
문제는 그 증명이 틀렸을 때 무엇이 벌어지느냐입니다.

## 정의되지 않은 동작 — 계약을 깨뜨렸을 때의 의미

**정의되지 않은 동작**(undefined behavior, UB)은 단순히 "프로그램이 크래시한다"는 뜻이 아닙니다.
그보다 훨씬 더 심각합니다.

[6장](/rust-opt/06-compiler/)에서 컴파일러 최적화는 "프로그램의 의미를 보존하는 변환"이라고 배웠습니다.
그 의미가 성립하는 전제에는 **UB가 발생하지 않는다는 가정**이 포함됩니다.
경계 검사 제거([7장](/rust-opt/07-zero-cost/))도, 에일리어싱 정보를 이용한 재배치(6장)도
"범위를 벗어난 접근은 없다", "`&mut`는 배타적이다" 같은 규칙이 항상 지켜진다는 전제에서 가능합니다.

UB를 일으킨 코드는 그 전제를 깨뜨립니다.
잘못된 전제에서는 어떤 결론이든 도출할 수 있듯이,
**UB가 발생한 뒤의 최적화된 프로그램에는 언어 차원의 동작 보장이 없습니다**.

직접 확인해 보겠습니다. 길이 3짜리 `Vec`의 일곱 번째 요소를 `get_unchecked`로 읽습니다.
명백한 UB입니다.

저자가 Playground에서 실행했을 때 프로그램은 크래시하지 않고
**`v[7] = 0`을 출력한 뒤 정상 종료**했습니다.
이것이 UB의 위험한 점입니다. 반드시 폭발하지 않습니다.
**그럴듯한 잘못된 값을 돌려주고 계속 실행될 수도 있습니다**.
테스트에서는 통과하다가 실제 데이터나 컴파일러 버전이 달라졌을 때 갑자기 문제가 나타날 수도 있습니다.
따라서 "실행해 보니 잘 된다"는 것은 `unsafe` 코드의 정확성을 증명하지 못합니다.

Rust에서 특히 주의해야 할 UB의 예를 정리해 보겠습니다.

- **데이터 레이스** — 동기화 없이 여러 스레드가 같은 메모리를 읽고 쓰는 경우([5장](/cpu/05-multicore/))
- **잘못된 메모리 접근** — 범위 밖 접근, 해제 후 사용(use-after-free), null 또는 정렬되지 않은 포인터 역참조
- **참조 규칙 위반** — 원시 포인터를 거치더라도 같은 데이터에 여러 `&mut`를 동시에 만들거나, `&`로만 접근 가능한 데이터를 임의로 변경하면 UB가 될 수 있습니다.
  참조는 생성되는 순간부터 유효하고 정렬되어 있으며 초기화된 값을 가리켜야 합니다
- **초기화되지 않은 메모리 읽기** — 초기화 전 영역은 `MaybeUninit<T>`처럼 "아직 `T`가 아닐 수 있음"을 타입으로 나타내야 하며,
  초기화가 끝나기 전에 `T`로 읽어서는 안 됩니다
- **유효하지 않은 값 만들기** — `bool`에 2를 넣거나 존재하지 않는 enum 판별자를 만들거나,
  올바르지 않은 UTF-8을 `str`로 취급하는 경우입니다. `transmute`는 이런 실수의 흔한 진입점입니다

## Miri — UB를 찾는 도구

직접 증명했다고 생각한 안전 조건을 기계적으로 검사하는 도구가 있습니다.
[Miri](https://github.com/rust-lang/miri)는 Rust 컴파일러의 중간 표현인 MIR
([6장](/rust-opt/06-compiler/))을 단계별로 해석 실행하면서
UB가 발생하는 순간 오류를 보고하는 인터프리터입니다.
앞의 실험을 Miri에서 실행하면 조용히 성공하는 대신 다음과 같은 오류를 볼 수 있습니다.

```text
error: Undefined Behavior: `assume` called with `false`
 --> src/main.rs:5:23
  |
5 |     let x = unsafe { *v.get_unchecked(i) };
  |                       ^^^^^^^^^^^^^^^^^^ Undefined Behavior occurred here
```

사용 방법은 `cargo +nightly miri test`처럼 테스트를 Miri 위에서 실행하는 것입니다.
Playground에서도 Tools 메뉴의 Miri 기능으로 확인할 수 있습니다.
참조 배타성처럼 미묘한 규칙도 Stacked Borrows라는 모델로 검사합니다.
후속 모델인 Tree Borrows도 `-Zmiri-tree-borrows`로 시험할 수 있습니다.

한계도 있습니다. Miri는 **실제로 실행된 경로만** 검사합니다.
따라서 테스트가 실행하지 않은 경로는 검사할 수 없고, FFI 호출 내부도 추적하지 못합니다.
또 일반 테스트보다 수십~수백 배 느릴 수 있습니다.
그럼에도 `unsafe`가 들어간 코드의 테스트를 Miri에서도 실행하는 것은 매우 강력한 안전망입니다.

## FFI — 다른 언어와의 경계

`unsafe`의 중요한 사용처 중 하나가 **FFI**(foreign function interface)입니다.
FFI는 C의 **ABI**(application binary interface), 즉 호출 규약
([1장](/cpu/01-how-code-runs/))과 데이터 배치 같은 기계어 수준의 약속을 통해 다른 언어와 상호 운용하는 방법입니다.
컴파일러는 C 함수 내부의 안전성을 검증할 수 없으므로 이런 호출은 `unsafe`입니다.

```rust
// extern 블록 = "이 시그니처의 함수가 링크 대상에 존재한다"는 선언
unsafe extern "C" {
    fn labs(x: c_long) -> c_long; // C 라이브러리 함수. long의 폭은 OS에 따라 다릅니다
}
```

먼저 "FFI 호출은 느린가"를 측정해 보겠습니다.
Rust의 `.abs()`와 같은 계산을 하는 C 라이브러리의 `labs`를 각각 1억 번 호출합니다.

저자가 Playground에서 측정했을 때 약 64밀리초와 약 80밀리초였습니다.
1억 번 호출해도 차이는 약 20% 수준입니다.
이 차이에는 FFI 경계뿐 아니라 인라인된 Rust 구현과 라이브러리 함수 구현 자체의 차이도 섞여 있으므로
정확한 "한 번 호출의 가격"으로 해석할 수는 없습니다.
하지만 결론은 충분히 분명합니다.
**FFI 호출 자체의 기계적 비용은 호출 규약을 따르는 일반 함수 호출과 비슷한 수준**이며,
대략 나노초 단위입니다.

진짜 비용은 다른 곳에 있습니다.

- **최적화 경계** — [6장](/rust-opt/06-compiler/)에서 보았듯이 인라이닝과 자동 벡터화는 경계를 넘기 어렵습니다.
  작은 함수를 매우 자주 호출하기보다는, 큰 단위의 작업을 한 번에 넘기는 편이 유리합니다
- **데이터 표현 변환** — Rust의 `String`은 NUL 종료가 아니므로 C 문자열로 넘기려면 `CString` 변환에 할당과 복사가 필요할 수 있습니다.
  구조체는 `#[repr(C)]`([2장](/cpu/02-memory-hierarchy/))으로 레이아웃을 고정합니다
- **소유권 규약** — 누가 할당하고 누가 해제할지는 ABI만 봐서는 알 수 없습니다.
  "C에서 받은 메모리는 C의 해제 함수로 돌려준다" 같은 규칙은 사람이 지켜야 합니다
- **패닉 차단** — Rust 패닉의 unwinding을 FFI 경계 바깥으로 흘려보내면 안 됩니다.
  `extern "C"` 함수 밖으로 unwind하려 하면 abort될 수 있으므로, Rust 콜백은 필요에 따라 `catch_unwind`로 경계를 막습니다

C 헤더에서 Rust 선언을 자동 생성하는 bindgen과,
반대로 Rust API에서 C 헤더를 생성하는 cbindgen이 널리 사용됩니다.

## unsafe를 운용하는 규칙

마지막으로 `unsafe` 코드를 작성할 때 지켜야 할 실무적인 규율을 정리합니다.
Rust 생태계에서 널리 받아들여지는 방식입니다.

- **범위를 최소화합니다** — `unsafe` 블록에는 정말로 안전 조건을 직접 증명해야 하는 연산만 넣고,
  한 블록에서는 한 가지 위험만 다루는 편이 좋습니다
- **SAFETY 주석을 남깁니다** — 왜 안전한지에 대한 증명을 바로 위에 적습니다.
  예: `// SAFETY: i는 바로 앞에서 len보다 작다고 검사했습니다`.
  clippy의 `undocumented_unsafe_blocks` 린트로 이를 강제할 수도 있습니다
- **안전한 추상화로 감쌉니다** — `unsafe`는 모듈 내부로 숨기고 외부에는 안전한 API만 공개합니다.
  `Vec`도 내부 구현에는 많은 `unsafe`가 있지만 사용자는 안전하게 쓸 수 있습니다.
  `len <= capacity` 같은 불변식을 모듈 경계 안에서 항상 유지하면 검증 범위도 그 안으로 제한됩니다
- **Miri로 검사합니다** — `unsafe`가 들어간 테스트는 가능하면 Miri에서도 실행합니다

## 정리

- `unsafe`는 특정 저수준 연산의 금지를 해제하고, 안전 조건을 증명할 책임을 프로그래머에게 넘깁니다.
  타입 검사나 빌림 검사가 사라지는 것은 아닙니다
- UB는 단순한 크래시가 아니라 컴파일러 최적화가 기대하는 전제의 붕괴입니다.
  실험에서는 범위를 벗어난 읽기가 조용히 0을 반환했습니다. "실행되니 맞다"는 증명이 될 수 없습니다
- Miri는 실제 실행 경로에서 UB를 탐지하는 강력한 도구입니다. `unsafe` 코드의 중요한 검사 수단입니다
- FFI 호출 자체는 일반 함수 호출과 비슷한 비용이었습니다.
  실제 비용은 최적화 경계, 표현 변환, 소유권 규칙, 패닉 처리에서 발생합니다
- `unsafe`는 작은 범위에 가두고, SAFETY 주석으로 증명을 남기며, 안전한 추상화 뒤에 숨기는 것이 기본 원칙입니다

다음 장에서는 코드를 바꾸지 않고도 성능과 크기를 조절할 수 있는 영역인
빌드 제어를 다룹니다. PGO, 링커, 컴파일 시간, 바이너리 크기를 살펴봅니다.
