- `BTreeMap`이 트리 구조인데도 해시 테이블보다 3배 이상 느린 이유와 그래도 선택해야 하는 경우

- 비트 연산으로 만든 가장 작은 자료구조인 비트셋과 실측 31배 차이
- 왜 이 내용이 필요한가 — [8장](/rust-opt/08-measure/)에서 최적화 우선순위의 맨 위에 둔 것이 "알고리즘과 자료구조"였습니다.
  이제 Big-O 표만이 아니라 구현과 상수 비용을 보고 선택할 수 있어야 합니다

시간 복잡도(Big-O 표기)는 n이 커질 때 비용이 어떻게 증가하는지만 알려 줍니다.
하지만 같은 O(1)이라도 캐시 미스가 한 번인지 열 번인지에 따라 실제 시간은 크게 달라질 수 있습니다.
이 장에서는 표준 자료구조의 "상수항"을 하드웨어 관점에서 살펴봅니다.

## HashMap의 내부 — SwissTable

Rust의 `HashMap` 구현(hashbrown)은 Google이 설계한 **SwissTable** 계열의
오픈 어드레싱(open addressing) 방식입니다. 핵심은 두 가지입니다.

첫 번째는 **제어 바이트 배열**입니다.
키와 값을 저장하는 본체 배열과 별도로, 각 슬롯의 상태를 1바이트씩 저장합니다.
빈 슬롯인지, 삭제된 슬롯인지, 해시값의 일부가 무엇인지 같은 정보를 담습니다.
검색할 때는 먼저 이 제어 바이트들을 **여러 개씩 묶어** SIMD 명령
([4장](/cpu/04-simd/))으로 비교합니다.
x86에서는 보통 16개, ARM64 NEON에서는 8개 단위로 후보를 좁힌 뒤 실제 키를 확인합니다.
키 본체에 접근하는 횟수를 줄여 캐시 라인([2장](/cpu/02-memory-hierarchy/)) 사용을 최소화하는 구조입니다.

두 번째는 **부하율과 리해시**입니다.
테이블이 너무 차면 더 큰 테이블을 만들어 원소를 다시 배치합니다.
이 과정은 [7장](/rust-opt/07-zero-cost/)에서 본 `Vec`의 성장과 같은 상환(amortized) 비용 구조를 가집니다.
대부분은 빠르지만 가끔 큰 비용이 발생합니다.
원소 수를 예상할 수 있다면 `with_capacity`를 미리 사용하는 전략이 여기에서도 효과적입니다.

### 해시 함수도 선택의 일부입니다

쉽게 놓치는 비용이 해시 함수입니다.
Rust의 기본 해시는 **SipHash** 계열로, 공격자가 의도적으로 충돌하는 키를 만들어
해시 테이블을 O(n)으로 느리게 만드는 **HashDoS** 공격에 대응하기 위해 설계되었습니다.
안전한 대신 단순한 정수 키 하나를 처리하는 데는 상대적으로 비싼 편입니다.

100만 개의 `u64` 키에 대해 100만 번 검색하는 실험을 해 보겠습니다.
다음 네 가지를 비교합니다.

1. 기본 `HashMap`
2. 해시 함수만 가벼운 구현으로 바꾼 `HashMap`
3. `BTreeMap`
4. 정렬된 `Vec`에서의 이진 탐색

해시 함수 교체 자체는 표준 `Hasher` 트레이트를 짧게 구현하면 가능합니다.
실무에서는 같은 목적의 [rustc-hash](https://github.com/rust-lang/rustc-hash)(FxHashMap)나 ahash를 많이 사용합니다.

<RustPlay code={maps} mode="release" title="같은 검색을 서로 다른 자료구조와 해시로 비교" />

저자가 Playground에서 측정한 결과입니다.

| 구조 | 시간 | 검색 1회 |
| --- | --- | --- |
| HashMap (기본 SipHash) | 65ms | 65ns |
| HashMap (가벼운 해시) | **25ms** | 25ns |
| BTreeMap | 210ms | 210ns |
| 정렬된 Vec 이진 탐색 | 93ms | 93ns |

**해시 함수만 바꿨는데 2.6배** 차이가 났습니다.
자료구조와 알고리즘은 그대로이고 키 하나를 해시하는 몇 나노초의 비용만 달라졌습니다.
O(1)의 "1" 안에도 큰 차이가 있을 수 있다는 좋은 예입니다.

사용 기준은 보안 요구와 데이터 출처에 따라 달라집니다.
외부에서 들어오는 키, 예를 들어 HTTP 헤더나 사용자 입력은 HashDoS 위험을 고려해 기본 해시를 유지하는 편이 안전합니다.
반대로 **프로그램 내부에서만 사용하는 정수나 짧은 키**는 Fx 계열처럼 빠른 해시를 선택할 수 있습니다.
rustc와 Firefox도 이런 종류의 최적화를 사용합니다.
코드의 `BuildHasherDefault<FastHasher>`는 `Default`로 만들 수 있는 `Hasher`를
`HashMap`이 요구하는 해시 생성기 형태로 연결하는 표준 어댑터입니다.

## BTreeMap의 실제 모습

`BTreeMap`은 B-트리입니다.
노드 하나가 여러 키를 가지고 여러 자식으로 분기하는 구조이며,
노드 내부는 연속 배열이라 캐시 라인을 고려한 현대적인 설계입니다.
그럼에도 실험에서는 한 번 검색에 약 210ns로 해시 테이블보다 3~8배 느렸습니다.

이유는 트리 구조에서 피하기 어려운 **포인터 추적**입니다.
100만 원소에서는 트리 깊이가 대략 몇 단계가 되며,
각 단계에서 서로 다른 캐시 라인으로 이동할 가능성이 큽니다.
반면 해시 테이블은 해시 계산 뒤 거의 한두 번의 메모리 접근으로 목표 슬롯에 도달할 수 있습니다.
메모리 계층을 사용하는 방식 자체가 다릅니다.

그렇다면 `BTreeMap`은 언제 선택할까요? **순서가 필요할 때**입니다.
범위 검색, 최솟값과 최댓값, 안정적인 정렬 순서로의 순회 같은 기능은 해시 테이블이 제공하기 어렵습니다.

또 하나의 선택지는 **데이터가 정적이라면 정렬된 `Vec` + 이진 탐색**입니다.
구조체 오버헤드가 거의 없고 메모리가 연속적이며 순서도 유지됩니다.
실험에서는 93ns로 `BTreeMap`의 절반보다 빨랐습니다.
생성 후 거의 변경하지 않는 인덱스라면 매우 좋은 선택입니다.
다만 삽입과 삭제가 자주 일어나면 `Vec`의 O(n) 이동 비용이 문제가 됩니다.

## 작은 n에서는 선형 탐색이 이길 수 있습니다

시간 복잡도 직감이 가장 쉽게 깨지는 영역은 n이 작은 경우입니다.
32개 원소를 가진 테이블에서 1000만 번 검색해 봅니다.
`HashMap`과 단순히 `Vec` 처음부터 끝까지 훑는 선형 탐색을 비교합니다.

<RustPlay code={smallN} mode="release" title="원소가 32개라면 어느 쪽이 빠를까?" />

저자가 Playground에서 측정했을 때 `HashMap`은 약 95밀리초,
**선형 탐색은 약 79밀리초**였습니다.

선형 탐색이 이길 수 있는 이유는 연속 메모리 접근으로 프리페치와 캐시를 잘 활용하고,
해시 계산이라는 고정 비용이 없기 때문입니다.
분기 예측이나 SIMD 최적화도 코드 형태와 데이터 분포에 따라 도움을 줄 수 있습니다.
정확한 손익분기점은 키 타입, 검색 성공률, 분포에 따라 달라지지만
**원소가 수십 개 수준이라면 단순한 구조가 더 빠를 수 있다**는 점은 기억할 만합니다.
경계는 항상 측정으로 확인해야 합니다.

비슷한 아이디어가 인라인 저장 컨테이너입니다.
[smallvec](https://github.com/servo/rust-smallvec)이나 `ArrayVec`은
원소가 적을 때 컨테이너 내부에 직접 저장해 [18장](/rust-deep/18-allocators/)의 힙 할당을 피하고,
용량을 넘으면 힙을 사용하는 하이브리드 구조입니다.
"대부분 2~3개 원소지만 가끔 많아진다"는 실제 분포에 잘 맞습니다.

대신 타입 자체가 커진다는 비용이 있습니다.
`SmallVec<[T; 16]>`은 항상 16개 원소를 담을 수 있는 공간을 구조체 안에 포함하기 때문에
이를 포함하는 다른 구조체나 `enum`([7장](/rust-opt/07-zero-cost/))도 커집니다.
인라인 용량은 실제 데이터 분포를 보고 정하는 편이 좋습니다.

## 비트를 직접 쓰기 — 가장 작은 자료구조

마지막은 자료구조라고 부르기도 어려울 만큼 단순한 도구인 비트입니다.
많은 현대 CPU는 설정된 비트 수를 세는 `count_ones`, 앞쪽 0의 개수를 세는 `leading_zeros` 같은 연산을
전용 명령(popcnt 등)으로 빠르게 처리합니다.

이를 집합 표현에 사용한 것이 **비트셋**(bitset)입니다.
0부터 1000만 사이의 정수 집합을 `HashSet<u32>`로 표현한 경우와,
`Vec<u64>`의 각 비트를 사용하는 경우를 비교합니다. 소속 여부를 2000만 번 검사합니다.

<RustPlay code={bitset} mode="release" title="집합 포함 여부: HashSet과 비트셋 비교" />

저자의 Playground 실측은 약 672밀리초와 약 22밀리초로 **31배 차이**였습니다.
비트셋의 검사는 시프트와 AND 정도만 필요하고, 분기도 해시도 없습니다.
1000만 개의 불리언 정보를 약 1.2MB, 원소당 1비트에 저장할 수 있어 캐시 효율도 뛰어납니다.
원소가 정수이고 범위가 유한하다면 매우 강력한 구조입니다.
범위가 매우 넓고 희소하다면 압축 비트맵인 [roaring](https://github.com/RoaringBitmap/roaring-rs)이 자주 사용됩니다.

:::note[문자열에서도 같은 아이디어가 적용됩니다]
문자열에도 같은 원리가 있습니다.
`String`은 자체 메타데이터와 힙 할당이 필요하므로 짧은 문자열은 `compact_str` 같은 인라인 저장 타입으로 힙을 피할 수 있습니다.
또 같은 문자열을 반복해서 비교하거나 저장한다면 **인터닝**(interning), 즉 문자열을 한 번만 저장하고 이후에는 정수 ID로 다루는 방식이 효과적입니다.
문자열 비교가 `u32` 비교 하나로 바뀌는 셈입니다. 이 장의 핵심 원리를 잘 보여 줍니다.
:::

## 정리

- `HashMap`은 SwissTable 계열 구조로 SIMD를 이용해 여러 슬롯을 한 번에 탐색합니다.
  해시 함수만 교체해도 2.6배 차이가 났습니다. 내부 정수 키에는 Fx 계열을 고려할 수 있고 외부 입력에는 기본 SipHash 계열이 안전한 선택입니다
- `BTreeMap`은 순서가 필요할 때 선택하는 구조입니다. 실험에서는 해시보다 3배 이상 느렸습니다.
  정적인 데이터라면 정렬된 `Vec` + 이진 탐색도 강력합니다
- 원소가 수십 개라면 선형 탐색이 해시 테이블을 이길 수 있습니다. 실험에서 32개 원소는 실제로 역전됐습니다.
  SmallVec 계열은 적은 원소를 인라인에 두는 최적화를 자동화합니다
- 정수 집합은 비트셋으로 표현했을 때 31배 빨랐습니다. 표현을 바꾸는 것이 가장 큰 최적화가 될 수 있습니다
