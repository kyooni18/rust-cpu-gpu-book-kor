이 장에서 알 수 있는 것:

- LTO와 `codegen-units`의 실제 트레이드오프: 빌드 17→39초, 바이너리 5.8→3.9MB
- PGO(profile-guided optimization)의 전체 절차와 실제 측정 결과
- 컴파일 시간을 줄이는 체계적인 방법 — 개발 반복 속도도 성능의 일부입니다
- 바이너리 크기 최소화(실측 422KB→279KB)와 그 대가
- 왜 이 내용이 필요한가 — 코드 한 줄을 바꾸지 않아도 얻을 수 있는 성능과,
  매일 기다리는 빌드 시간은 모두 빌드 설정에 크게 좌우됩니다.
  [6장](/rust-opt/06-compiler/)에서 소개한 설정을 실제 측정으로 완성합니다

이 장의 측정은 저자의 Mac(Apple M4)에서 수행했습니다.
빌드 시간은 머신과 캐시 상태에 크게 의존하므로 절대값보다 비율을 중심으로 보세요.

## release 프로파일을 실제로 비교하기

[6장](/rust-opt/06-compiler/)에서 성능을 우선한다면 `lto = "thin"`, `codegen-units = 1`을 고려할 수 있다고 했습니다.
그 대가를 숫자로 확인해 보겠습니다.
이 책의 `examples` 전체를 wgpu 의존성까지 포함해 클린 빌드한 결과입니다.

| 설정 | 클린 빌드 | 바이너리 크기 |
| --- | --- | --- |
| lto=off, codegen-units=16 (Cargo 기본) | 17초 | 5.8MB |
| lto=thin, codegen-units=1 (6장의 권장안) | 29초 | 4.6MB |
| lto=fat, codegen-units=1 | 39초 | 3.9MB |

LTO를 강하게 적용할수록 빌드 시간은 늘고 바이너리는 작아졌습니다.
크레이트 경계를 넘어 코드가 합쳐지고 중복이 제거되기 때문입니다.
실행 속도에 미치는 영향은 프로그램 구조에 따라 달라집니다.
크레이트 경계를 매우 자주 넘는 호출이 많을수록 효과가 커질 수 있고,
이 책의 행렬 곱처럼 핫 루프가 한 크레이트 안에 갇힌 코드에서는 차이가 작을 수 있습니다.
판단은 [8장](/rust-opt/08-measure/)의 원칙대로 측정해야 합니다.

실무에서는 프로파일을 목적별로 나누는 방식이 유용합니다.

```toml
[profile.release]          # 일상적인 release 빌드: 빠른 반복을 위해 기본값 중심

[profile.dist]             # 배포용: 빌드 시간을 더 써서 최적화
inherits = "release"
lto = "thin"
codegen-units = 1
```

## PGO — 절차와 현실적인 효과

**PGO**(profile-guided optimization, [6장](/rust-opt/06-compiler/))는
프로그램이 실제로 어떻게 실행됐는지에 대한 통계를 컴파일러에 제공하는 방법입니다.
과정은 네 단계입니다.

```sh
# 0. 이전 프로파일을 제거합니다
rm -rf /tmp/pgo-data

# 1. 프로파일 수집 코드를 넣어 빌드합니다
#    --target을 명시하면 빌드 스크립트 자체의 실행이
#    프로파일에 섞이는 것을 줄일 수 있습니다
RUSTFLAGS="-Cprofile-generate=/tmp/pgo-data" cargo build --release

# 2. 실제 사용 패턴을 대표하는 워크로드를 실행합니다
./target/release/myapp --typical-workload

# 3. 프로파일 파일을 하나로 합칩니다
#    llvm-profdata는 `rustup component add llvm-tools`로 설치할 수 있습니다
#    PATH 밖에 있을 수 있으므로 ~/.rustup/toolchains/*/lib/rustlib/*/bin/에서 찾습니다
llvm-profdata merge -o /tmp/pgo-data/merged.profdata /tmp/pgo-data

# 4. 수집한 프로파일을 사용해 다시 빌드합니다
RUSTFLAGS="-Cprofile-use=/tmp/pgo-data/merged.profdata" cargo build --release
```

컴파일러는 실제 분기 빈도와 실행 패턴을 바탕으로 핫 코드 배치
([16장](/cpu-deep/16-frontend/)의 프런트엔드 최적화), 인라이닝 판단,
일부 간접 호출의 직접화 등을 시도합니다.

저자의 실제 측정 결과도 보겠습니다.
편향된 간접 호출을 5000만 번 실행하는 마이크로벤치마크에서 PGO를 적용했더니
기본 버전 약 70밀리초, PGO 버전 약 75밀리초로 **개선되지 않았습니다**.
작은 프로그램에서는 정적 분석만으로도 컴파일러가 이미 좋은 결정을 내리는 경우가 많아
PGO가 추가로 할 일이 거의 없었던 것입니다.

PGO가 유의미하게 작동하는 사례는 컴파일러, 브라우저, 대형 서버처럼
코드가 크고 분기 패턴이 다양하며 명령어 캐시가 중요한 프로그램에서 더 자주 나타납니다.
rustc 자체도 PGO를 활용해 빌드됩니다.
일반적으로 기대하는 개선폭도 몇 퍼센트에서 십여 퍼센트 정도로,
**마법이라기보다 대규모 코드의 배치와 판단을 실제 사용 패턴에 맞추는 과정**에 가깝습니다.
[cargo-pgo](https://github.com/Kobzol/cargo-pgo)는 이 절차를 자동화해 줍니다.
더 나아가 링크된 바이너리의 코드를 실행 프로파일에 맞춰 재배치하는 BOLT도 있으며 cargo-pgo가 지원합니다.

## 컴파일 시간도 성능입니다

Rust의 긴 컴파일 시간은 개발 반복을 직접 느리게 만듭니다.
원인과 대책을 체계적으로 살펴보겠습니다.

먼저 측정합니다. [8장](/rust-opt/08-measure/)의 원칙은 빌드에도 그대로 적용됩니다.

```sh
cargo build --timings   # 크레이트별 빌드 시간을 HTML 보고서로 출력
```

주요 원인과 대책은 다음과 같습니다.

- **의존 크레이트 수** — `--timings`에서 시간이 많이 드는 의존성을 확인하고,
  필요 없는 의존성과 feature를 제거합니다. `default-features = false`도 고려할 수 있습니다.
  의존성은 실행 시간뿐 아니라 빌드 시간에도 비용을 만듭니다
- **단형화 폭발** — [7장](/rust-opt/07-zero-cost/)에서 보았듯이 제네릭 코드는 사용하는 타입마다 복제될 수 있습니다.
  큰 제네릭 함수라면 타입에 의존하지 않는 본문을 비제네릭 내부 함수로 분리하면 코드 생성량을 크게 줄일 수 있습니다.
  컴파일 시간과 바이너리 크기가 중요한 경계에서는 `dyn`을 사용해 실행 시 비용과 맞바꾸는 것도 합리적일 수 있습니다
- **링크 시간** — 대형 프로젝트에서는 링커 선택이 큰 차이를 만듭니다.
  Linux에서는 `mold`가 널리 쓰이고, macOS의 기본 링커도 최근 세대에서 크게 빨라졌습니다.
  인크리멘털 빌드 마지막 단계는 링크가 차지하는 비율이 높아 체감 효과가 큽니다
- **개발 루프에 맞는 명령 선택** — 타입 검사만 필요하다면 `cargo check`를 사용하면 코드 생성을 생략할 수 있습니다.
  rust-analyzer도 비슷한 경로를 활용합니다. CI에서는 sccache 같은 컴파일 캐시가 효과적일 수 있습니다

## 바이너리 크기 줄이기

크기를 우선하는 별도 프로파일을 만들어 작은 CLI 벤치마크에서 측정했습니다.

```toml
[profile.min-size]
inherits = "release"
opt-level = "z"     # 크기 우선 최적화
lto = "fat"
panic = "abort"     # unwinding 제거(6장)
strip = true         # 심볼 정보 제거
```

결과는 **422KB에서 279KB로 약 34% 감소**했습니다.
대신 실행 시간은 약 70밀리초에서 약 90밀리초로 느려졌습니다.
`opt-level = "z"`는 루프 언롤링과 인라이닝을 억제하는 경향이 있기 때문에
**바이너리 크기와 실행 속도 사이에는 분명한 트레이드오프**가 있습니다.
다만 [16장](/cpu-deep/16-frontend/)에서 보았듯이 코드가 매우 커서 명령어 캐시가 병목인 경우에는
작은 바이너리가 오히려 빨라질 수도 있습니다. 결국 측정이 필요합니다.

무엇이 바이너리 크기를 차지하는지는 [cargo-bloat](https://github.com/RazrFalcon/cargo-bloat)로
함수 단위까지 확인할 수 있습니다.
흔한 원인은 단형화된 코드의 중복, `Debug`와 포매팅 관련 코드,
그리고 Rust가 표준 라이브러리 일부를 정적으로 링크하면서 포함되는 코드입니다.
크기가 극도로 중요한 임베디드나 WebAssembly 환경에서는 `no_std`라는 선택지도 있습니다.
여기서는 개념만 소개합니다.

## 정리

- LTO와 `codegen-units`는 빌드 시간과 바이너리 크기, 경우에 따라 실행 속도를 맞바꾸는 다이얼입니다.
  실험에서는 빌드가 17→39초, 바이너리는 5.8→3.9MB 범위로 변했습니다.
  일상용과 배포용 프로파일을 나누는 것이 실용적입니다
- PGO는 네 단계 절차로 적용할 수 있지만 작은 프로그램에서는 효과가 없을 수도 있습니다.
  실험에서도 개선이 없었습니다. 큰 프로그램의 실제 실행 패턴을 반영하는 최적화라고 보는 편이 정확합니다
- 컴파일 시간은 `--timings`로 측정하고, 의존성 축소, 단형화 억제, 빠른 링커, `cargo check` 등으로 줄일 수 있습니다
- 크기 최적화 설정으로 바이너리를 약 34% 줄였지만 실행 시간은 70→90밀리초로 악화됐습니다.
  크기와 속도도 측정하며 선택해야 합니다
