이 장에서 알 수 있는 것:

- `Box::new`나 `Vec` 할당 뒤에서 동작하는 할당자의 내부 구조: 크기 클래스, 프리 리스트, 스레드 캐시
- 할당이 "대부분 몇 나노초지만 가끔 갑자기 느려지는" 이유
- 전역 할당자를 교체하는 방법과 실제 효과, 그리고 한계
- 아레나 할당 — 한꺼번에 할당하고 한꺼번에 버리는 방식(실측: 해제가 약 6000배 빠름)
- 왜 이 내용이 필요한가 — [7장](/rust-opt/07-zero-cost/)에서는 실제 성능 비용이 힙 할당에서 생기는 경우가 많다고 결론 내렸습니다.
  내부 구조와 제어 방법을 알아야 `with_capacity`를 넘어 더 근본적인 최적화를 할 수 있습니다

## 할당자는 무엇을 할까

`Box::new(x)`를 호출하면 메모리는 어디에서 올까요?

답은 **할당자**(allocator)입니다.
프로그램 안에서 힙 메모리를 관리하는 계층입니다.
할당자는 운영체제에서 비교적 큰 메모리 영역을 한꺼번에 확보하고,
이를 작은 조각으로 나눠 `Box`, `Vec`, `String` 같은 객체에 제공합니다.
운영체제에 매번 시스템 호출을 하는 것은 비싸기 때문에,
큰 덩어리를 받아 내부에서 잘게 나눠 쓰는 것이 핵심 역할입니다.
이 큰 영역은 [14장](/cpu-deep/14-virtual-memory/)의 `mmap` 같은 메커니즘을 통해 페이지 단위로 얻을 수 있습니다.

현대의 대표적인 할당자인 glibc malloc, macOS libmalloc, jemalloc, mimalloc 등은
세부 구현은 달라도 대체로 비슷한 구조를 갖습니다.

- **크기 클래스**(size class) — 요청한 크기를 16B, 32B, 48B 같은 규격 크기로 올림한 뒤 클래스별로 재사용 가능한 블록을 관리합니다.
  검색 비용을 줄일 수 있지만 올림 때문에 남는 공간이 생기며, 이를 **내부 단편화**라고 부릅니다
- **프리 리스트**(free list) — 해제된 작은 블록을 크기 클래스별 연결 구조로 관리합니다
- **스레드 로컬 캐시** — 스레드마다 재사용 가능한 작은 블록을 따로 보관해 대부분의 할당과 해제를 락 없이 처리합니다.
  [5장](/cpu/05-multicore/)에서 본 "공유를 줄이면 빠르다"는 원칙이 여기에도 적용됩니다
- **큰 할당의 별도 처리** — 일정 크기 이상의 요청은 운영체제에서 직접 확보하고 직접 반환하는 경우가 많습니다.
  실제 기준은 할당자와 실행 이력에 따라 달라질 수 있습니다

이 구조를 알면 할당 비용이 왜 일정하지 않은지도 이해할 수 있습니다.

**빠른 경로**에서는 스레드 캐시에 이미 빈 블록이 있어 포인터 하나를 꺼내기만 하면 됩니다.
수 나노초 정도로 끝날 수 있습니다.
반대로 **느린 경로**에서는 스레드 캐시를 보충하거나 다른 스레드와 블록을 주고받거나,
운영체제에서 새 메모리를 가져와야 해서 수백 나노초에서 마이크로초까지 걸릴 수 있습니다.
새로 확보한 페이지라면 [14장](/cpu-deep/14-virtual-memory/)에서 본 초기 페이지 폴트 비용도 뒤따를 수 있습니다.

오랫동안 실행되는 프로세스에서는 **외부 단편화**도 문제가 됩니다.
사용 중인 작은 블록이 여기저기 남아 큰 연속 공간을 만들기 어려워지는 현상입니다.

## 전역 할당자 교체하기

Rust에서는 전역 할당자를 간단히 바꿀 수 있습니다.

```rust
use mimalloc::MiMalloc;

#[global_allocator]
static GLOBAL: MiMalloc = MiMalloc;
```

이렇게 하면 프로그램에서 사용하는 대부분의 `Box`, `Vec`, `String`이
[mimalloc](https://github.com/microsoft/mimalloc)을 통해 메모리를 할당하게 됩니다.
jemalloc 같은 다른 할당자도 비슷한 방식으로 적용할 수 있습니다.

효과는 환경에 따라 크게 달라집니다.
저자가 Mac(Apple M4)에서 8개 스레드가 작은 `Vec`를 반복해서 할당·해제하는 작업을
총 1600만 번 수행했을 때 결과는 다음과 같았습니다.

```text
시스템 기본 : 61.8ms
mimalloc    : 54.9ms   (약 1.1배)
```

이 환경에서는 **약 1.1배**로 차이가 크지 않았습니다.
할당한 스레드와 해제하는 스레드를 다르게 만든 실험에서도
채널 통신 비용에 묻혀 유의미한 차이가 거의 나타나지 않았습니다.
macOS 기본 할당자가 이미 잘 최적화되어 있고,
이 작업이 대부분 빠른 경로에서 처리되었기 때문입니다.

그럼에도 할당자 교체가 자주 시도되는 이유는
**환경에 따라 효과가 크게 나타날 수 있기 때문**입니다.
멀티스레드 할당이 많은 Linux 워크로드에서는 jemalloc이나 mimalloc로 바꿔
두 자릿수 퍼센트 이상 개선되는 사례도 있습니다.
적용과 되돌리기가 매우 쉬우므로 [8장](/rust-opt/08-measure/)의 원칙대로
직접 측정해 판단하면 됩니다.

## 아레나 — 한꺼번에 할당하고 한꺼번에 버리기

전역 할당자 교체보다 더 근본적인 방법이 **아레나 할당**(arena allocation)입니다.
아이디어는 단순합니다.

작은 객체를 하나씩 할당하고 하나씩 해제하지 말고,
**수명이 비슷한 객체들을 큰 영역 하나에 모아 두고 마지막에 전체를 한 번에 버립니다.**

아레나 내부에서 새 객체를 할당할 때는 현재 위치를 가리키는 포인터나 인덱스를 앞으로 옮기기만 하면 됩니다.
이 방식을 **범프 할당**(bump allocation)이라고 부릅니다.
크기 클래스나 프리 리스트를 탐색할 필요가 없습니다.

실험에서는 100만 개 노드로 연결 리스트를 두 방식으로 만듭니다.
첫 번째는 노드마다 `Box`로 개별 할당하고,
두 번째는 하나의 `Vec`를 아레나처럼 사용해 인덱스로 노드를 연결합니다.
구축, 순회, 해제 시간을 각각 측정합니다.

저자가 Playground에서 측정한 결과입니다.

| | Box(개별 할당) | 아레나(Vec) | 차이 |
| --- | --- | --- | --- |
| 구축 | 34.5ms | 9.8ms | 3.5배 |
| 순회 | 3.0ms | 2.1ms | 1.4배 |
| 해제 | 9.5ms | **1.5µs** | **약 6000배** |

구축 단계에서도 100만 번의 할당자 호출이 사라져 큰 차이가 나지만,
가장 눈에 띄는 부분은 **해제**입니다.
`Box` 방식은 100만 개 노드를 하나씩 프리 리스트로 돌려보내야 하지만,
아레나 방식은 `Vec` 하나만 반환하면 됩니다.

다만 이 결과는 요소 자체에 별도의 `Drop` 구현이 없는 경우입니다.
각 원소가 소멸자를 갖고 있다면 아레나를 사용해도 원소 수만큼 `Drop` 실행 비용은 남습니다.
즉 **drop도 무료는 아닙니다**.
큰 자료구조가 함수 끝에서 한꺼번에 해제되면서 지연 시간이 튀는 현상은
프로파일링에서 실제로 자주 발견됩니다.

아레나가 특히 잘 맞는 경우는 **수명이 같은 작은 객체가 매우 많이 생기는 작업**입니다.

- 웹 서버에서 요청 하나를 처리하는 동안 만드는 임시 객체들
- 컴파일러나 파서가 한 번의 분석 과정에서 만드는 AST 노드들
- 게임에서 한 프레임 동안만 필요한 임시 데이터

대표적인 크레이트로는 [bumpalo](https://github.com/fitzgen/bumpalo)와 `typed-arena`가 있습니다.
`bumpalo::Bump::alloc`은 아레나 수명에 묶인 참조를 반환하므로,
아레나보다 오래 살아남는 참조를 Rust의 라이프타임 시스템이 컴파일 시점에 막아 줍니다.
수명을 묶어서 관리하는 아레나 설계와 Rust의 라이프타임은 매우 잘 어울립니다.

또한 이 장의 실험처럼 **`Vec` + 인덱스**를 아레나처럼 쓰는 방법도 Rust에서 흔합니다.
참조 대신 `u32` 같은 인덱스를 사용하면 복잡한 자기참조 구조에서 빌림 검사와 충돌하는 일이 줄어듭니다.
인덱스는 포인터보다 작을 수도 있어 [2장](/cpu/02-memory-hierarchy/)의 캐시 효율에도 도움이 되고,
직렬화도 쉬워집니다.
그래프, 게임의 ECS(entity component system) 같은 구조에서 자주 사용하는 방식입니다.

## 정리

- 할당자는 운영체제에서 큰 영역을 받아 작은 블록으로 나눠 제공합니다.
  크기 클래스와 스레드 캐시 덕분에 평소에는 수 나노초 수준으로 빠르지만,
  보충이나 운영체제 접근이 필요한 순간에는 갑자기 느려질 수 있습니다
- `#[global_allocator]`로 전역 할당자를 쉽게 바꿀 수 있습니다.
  효과는 환경 의존적이며 저자의 macOS 환경에서는 약 1.1배였습니다. 직접 측정해서 판단해야 합니다
- 수명이 비슷한 많은 객체는 아레나가 효과적입니다.
  실험에서는 구축이 3.5배 빨라지고 해제는 약 6000배 빨랐습니다
- `Drop`에도 비용이 있습니다. 개별 객체 수가 많으면 해제 자체가 눈에 띄는 병목이 될 수 있습니다

다음 장에서는 Rust의 또 다른 핵심 주제인 `async`/`await`를 다룹니다.
비동기 함수가 실제 실행 시 어떤 상태 머신으로 바뀌고,
런타임이 수많은 작업을 어떻게 한정된 스레드 위에서 움직이는지 살펴보겠습니다.
