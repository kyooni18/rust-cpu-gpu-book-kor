## 왜 벽시계만으로는 부족할까

지금까지 GPU 시간을 잴 때는 `submit`한 뒤 완료를 기다릴 때까지의 벽시계 시간을 사용했습니다.
이 값에는 실제 커널 실행뿐 아니라 명령 전달, 큐 대기, 완료 알림,
CPU 측 동기화([24장](/gpu-deep/24-overlap/))까지 모두 들어갑니다.
큰 커널에서는 이런 오버헤드가 상대적으로 작지만,
작은 커널에서는 **측정값 대부분이 커널 바깥 비용**일 수 있습니다.

해결 방법은 **GPU 자체가 시간을 기록하게 하는 것**입니다.

## 타임스탬프 쿼리 구현

WebGPU의 **타임스탬프 쿼리**(timestamp query)는
명령 스트림의 특정 지점에서 GPU 내부 시계 값을 기록합니다.
wgpu에서는 대략 네 단계로 사용합니다.
전체 코드는 저장소 예제를 참고하세요.

```rust
// 1. 기능 지원을 확인하고 요청합니다
//    Features::TIMESTAMP_QUERY

// 2. 타임스탬프 두 개를 저장할 QuerySet을 만듭니다
let query_set = device.create_query_set(&wgpu::QuerySetDescriptor {
    ty: wgpu::QueryType::Timestamp,
    count: 2,
    label: None,
});

// 3. 컴퓨트 패스 시작과 끝에서 타임스탬프를 기록합니다
let mut pass = encoder.begin_compute_pass(&wgpu::ComputePassDescriptor {
    timestamp_writes: Some(wgpu::ComputePassTimestampWrites {
        query_set: &query_set,
        beginning_of_pass_write_index: Some(0),
        end_of_pass_write_index: Some(1),
    }),
    label: None,
});

// 4. 결과(u64 두 개)를 버퍼로 resolve한 뒤 읽어옵니다
encoder.resolve_query_set(&query_set, 0..2, &buf_resolve, 0);
// 경과 시간(ns) = (t1 - t0) × queue.get_timestamp_period()
```

GPU가 기록한 값은 나노초가 아니라 하드웨어 고유의 tick입니다.
따라서 `queue.get_timestamp_period()`로 한 tick이 몇 나노초인지 받아 환산해야 합니다.

## 실측 — 커널 시간과 벽시계의 차이

같은 커널을 큰 작업과 아주 작은 작업에서 실행해
GPU 시계로 잰 커널 시간과 CPU 벽시계를 비교합니다.
저자의 Apple M4 실측입니다.

```text
16M 원소 커널(GPU 시계):  9.9~11.3ms | 벽시계: 10.3ms
256 원소 커널(GPU 시계):    0.0043ms | 벽시계:  0.19ms
```

두 번째 줄이 핵심입니다.
실제 커널은 **4.3마이크로초**만 실행됐지만 벽시계는 **190마이크로초**였습니다.
약 **45배** 차이입니다.

[11장](/gpu/11-wgpu/)에서 작은 벡터 덧셈이 API 왕복 비용에 묻힌다고 설명했습니다.
이 실험이 그 차이를 숫자로 보여 줍니다.
벽시계만 보고 "커널 자체가 0.2밀리초 걸린다"고 생각한다면
실제로 존재하지 않는 대부분의 시간을 최적화하려고 하게 됩니다.
반대로 큰 작업에서는 커널 시간과 벽시계가 거의 같아지고 고정 오버헤드는 상대적으로 작아집니다.

따라서 **무엇을 측정하려는지에 따라 계측기를 선택해야 합니다**.
커널 처리량을 알고 싶다면 타임스탬프 쿼리,
사용자가 느끼는 전체 지연 시간을 알고 싶다면 벽시계가 필요합니다.
8장의 "내가 무엇을 재고 있는지 이해하라"는 원칙의 GPU 버전입니다.

## GPU 측정의 함정

실험에서는 흥미로운 이상값도 나왔습니다.
16M 원소 측정 첫 실행에서 **GPU 커널 시간이 26.6ms인데 벽시계가 13.5ms**라는
물리적으로 말이 되지 않는 값이 한 번 관측됐습니다.
이후 반복에서는 정상 범위로 돌아왔습니다.

정확한 원인은 확정하지 못했습니다.
GPU도 CPU처럼 부하에 따라 클록이 변하고,
`get_timestamp_period()`가 사용하는 환산값이 백엔드에서 근사치일 가능성도 있습니다.
실무적인 대응은 [8장](/rust-opt/08-measure/)과 같습니다.
**워밍업하고, 여러 번 측정하고, 비정상적인 값은 의심합니다**.

또 하나의 함정은 **비동기 실행**입니다.
타임스탬프는 컴퓨트 패스의 시작과 끝을 기록하지만 GPU는 여러 작업을 겹쳐 실행할 수 있습니다.
인접한 작업과 겹친 실행 상황이 측정에 영향을 줄 수 있으므로
커널 하나의 순수한 성능을 정확히 보고 싶다면 단독 submit으로 측정하는 것이 안전합니다.
[24장](/gpu-deep/24-overlap/)의 작업 겹치기는 실제 성능에는 도움이 되지만
개별 커널 측정에는 오히려 변수를 늘릴 수 있습니다.

## 프로파일러 — 더 깊게 보기

타임스탬프 쿼리는 [8장](/rust-opt/08-measure/)의 `Instant`와 비슷한 기본 계측 도구입니다.
더 깊이 분석하려면 GPU 전용 프로파일러를 사용합니다.

- **Xcode GPU Debugger / Metal System Trace**(macOS) — 패스별 시간, 점유율, 대역폭, 셰이더 병목을 GUI에서 분석할 수 있습니다.
  wgpu의 Metal 백엔드도 추적할 수 있습니다
- **NVIDIA Nsight Systems / Nsight Compute** — CUDA와 Vulkan 계열에서 널리 사용하는 도구입니다.
  Nsight Compute는 커널을 [10장](/gpu/10-gpu-memory/)의 루프라인 모델 위에 배치해 분석할 수 있습니다
- **[wgpu-profiler](https://github.com/Wumpf/wgpu-profiler)** — 이 장의 타임스탬프 쿼리 처리를 범위별로 자동화한 Rust 크레이트입니다

[16장](/cpu-deep/16-frontend/)의 top-down 분석처럼
GPU에서도 연산 한계인지, 메모리 대역폭 한계인지, 점유율 부족인지 구분해야 합니다.
이 책에서 배운 점유율, 코얼레싱, 산술 강도 같은 용어가 그대로 프로파일러의 지표를 읽는 언어가 됩니다.

## 정리

- GPU 커널의 정확한 시간은 GPU 자체 시계인 타임스탬프 쿼리로 측정할 수 있습니다.
  wgpu에서는 QuerySet, `timestamp_writes`, `resolve_query_set`을 사용합니다
- 아주 작은 커널에서는 벽시계가 실제 커널 시간보다 45배 길었습니다.
  처리량은 GPU 시계, 전체 지연 시간은 벽시계처럼 목적에 맞춰 측정해야 합니다
- GPU도 클록 변동과 비동기성 때문에 측정값이 흔들릴 수 있습니다.
  워밍업과 반복 측정이라는 8장의 규칙이 그대로 필요합니다
- 더 깊은 분석에는 Xcode GPU 도구나 NVIDIA Nsight 같은 프로파일러를 사용합니다.
  이 책에서 배운 GPU 용어가 분석 화면을 읽는 기준이 됩니다
