이 장에서 알 수 있는 것:

- GPU에서 모든 원소를 하나의 값으로 합치는 **reduction**의 대표적인 세 단계 구현
- atomic 경쟁, 배리어 비용, 스레드 조대화라는 커널 설계 용어
- 교과서의 정석이 실제 GPU에서는 뒤집힐 수 있다는 실측과 이를 해석하는 방법
- subgroup 명령이라는 다음 선택지
- 왜 이 내용이 필요한가 — [12장](/gpu/12-cpu-vs-gpu/)의 행렬 곱은 원소별로 독립적인 계산이었습니다.
  GPU의 또 다른 기본 형태인 "많은 결과를 하나로 합치는" 계산까지 알아야 커널 설계의 기본 어휘가 완성됩니다

이 장의 실험은 저장소의 `examples/ch23-reduction`에서 실행할 수 있습니다.

```sh
cd examples
cargo run --release -p ch23-reduction
```

측정 환경은 저자의 Mac(Apple M4)입니다.
공유 환경은 아니지만 실행마다 수십 퍼센트 정도 흔들릴 수 있어 결과는 대략적인 범위로 표시합니다.

## 예제 — reduction

**리덕션**(reduction, 집계)은 배열 전체를 하나의 값으로 합치는 연산입니다.
합계, 최댓값, 평균 등이 모두 같은 구조를 가집니다.
CPU에서는 `iter().sum()` 한 줄로 표현할 수 있지만,
[4장](/cpu/04-simd/)에서 보았듯이 그 내부에도 SIMD와 ILP 최적화가 숨어 있습니다.

GPU에서는 상황이 더 복잡합니다.
수백만 개의 스레드가 계산한 값을 **하나로 모아야 하기 때문**입니다.
GPU는 독립적인 계산을 병렬로 실행하는 데 강하지만,
"모으기"는 공유와 동기화([5장](/cpu/05-multicore/))를 필요로 합니다.

예제는 1677만 개, 약 64MB의 `u32` 배열 합계입니다.
CPU 한 코어에서 측정한 기준은 약 2~3밀리초입니다.
자동 벡터화된 꽤 강한 기준선입니다.

## v1 — 모든 스레드가 하나의 atomic 변수에 더하기

가장 단순한 방법은 스레드 하나가 원소 하나를 읽고,
전역 합계 변수에 `atomicAdd`를 실행하는 것입니다.

```wgsl
@compute @workgroup_size(256)
fn reduce_atomic(...) {
    let i = /* 자신이 담당하는 인덱스 */;
    if (i < arrayLength(&input)) {
        atomicAdd(&result, input[i]);
    }
}
```

1677만 번의 원자적 연산이 하나의 변수에 집중됩니다.
[17장](/cpu-deep/17-memory-model/)에서 본 RMW 경쟁을 1677만 개 GPU 스레드가 동시에 만드는 셈입니다.
전통적인 GPU 교재에서는 피해야 할 설계의 대표 사례로 자주 소개됩니다.

실측은 **약 2~4밀리초**였습니다.
예상보다 나쁘지 않고 CPU 한 코어와 비슷한 수준입니다.
이유는 뒤에서 다시 살펴봅니다.

## v2 — 공유 메모리의 트리로 합치기

교과서적인 방법은 워크그룹 안에서 먼저 값을 합치는 것입니다.
256개 스레드의 값을 공유 메모리([10장](/gpu/10-gpu-memory/))에 저장한 뒤
256→128→64→...→1처럼 절반씩 합치는 트리를 만듭니다.
마지막에 그룹 대표 스레드 하나만 전역 `atomicAdd`를 실행합니다.
이렇게 하면 원자적 연산은 약 65,536번, 즉 워크그룹 수만큼으로 줄어듭니다.

```wgsl
var<workgroup> partial: array<u32, 256>;

@compute @workgroup_size(256)
fn reduce_shared(...) {
    partial[lid.x] = /* 담당 원소 */;
    workgroupBarrier();
    var stride = 128u;
    while (stride > 0u) {
        if (lid.x < stride) {
            partial[lid.x] += partial[lid.x + stride];
        }
        workgroupBarrier(); // 각 단계에서 모든 스레드가 도착할 때까지 기다립니다
        stride = stride / 2u;
    }
    if (lid.x == 0u) { atomicAdd(&result, partial[0]); }
}
```

실측은 **약 5~15밀리초**였습니다.
놀랍게도 **매번 v1보다 두 배 이상 느렸습니다**.

이유를 보면 한 스레드가 실제로 하는 일은 원소 하나를 읽는 것뿐인데,
그 뒤 여덟 단계의 트리마다 `workgroupBarrier()`를 실행합니다.
배리어는 워크그룹 전체가 도착할 때까지 기다리는 동기화 지점이므로
워프([9장](/gpu/09-gpu-architecture/)) 실행이 계속 멈춥니다.
**실제 계산량은 적고 동기화 횟수는 너무 많습니다.**
[12장](/gpu/12-cpu-vs-gpu/)에서 본 "스레드 하나의 일이 너무 얇다"는 문제가
이번에는 동기화 비용 형태로 나타났습니다.

## v3 — 레지스터에서 먼저 묶고 나중에 합치기

해법은 [12장](/gpu/12-cpu-vs-gpu/)과 비슷합니다.
**스레드 조대화**(thread coarsening), 즉 스레드 하나가 더 많은 작업을 담당하게 만듭니다.

전체 스레드 수를 약 26만 개로 줄이고,
각 스레드가 먼저 **64개 원소를 레지스터에서** 합합니다.
이 구간에는 atomic도 배리어도 없습니다.
그 뒤에만 공유 메모리 트리와 atomic을 사용합니다.

```wgsl
var sum = 0u;
var i = /* 자신의 시작 위치 */;
while (i < n) {
    sum += input[i];
    i += 전체 스레드 수; // 그리드 스트라이드 루프
}
// 전체 작업 대부분은 여기까지 끝났습니다. 남은 부분만 트리로 합칩니다
```

인덱스를 전체 스레드 수만큼씩 증가시키는 **그리드 스트라이드 루프**(grid-stride loop)를 사용합니다.
이 방식은 인접한 스레드가 같은 반복에서 인접한 원소를 읽게 만들어
코얼레싱([10장](/gpu/10-gpu-memory/))을 유지할 수 있습니다.

실측은 **약 1~2밀리초, 가장 빠른 경우 0.98밀리초**였습니다.
v1보다 약 3배, v2보다 약 8배 빠르고 CPU 한 코어보다 약 2배 빠릅니다.
64MB를 약 1밀리초에 읽는 것이므로 실효 메모리 대역폭은 대략 50~65GB/s입니다.
합계는 산술 강도가 매우 낮은 작업이기 때문에
[10장](/gpu/10-gpu-memory/)의 루프라인 모델에서 메모리 대역폭 한계에 가까워진 결과라고 볼 수 있습니다.

## 정석은 하드웨어의 비용 구조를 전제로 합니다

이 실험에서 가장 중요한 점은 단순한 순위가 아닙니다.
**v1이 충분히 빠르고 v2가 느렸다는 결과가 전통적인 GPU 정석과 반대**라는 점입니다.

고전적인 GPU 최적화에서는 동일 주소에 대한 전역 atomic 경쟁이 매우 비싸고,
공유 메모리 트리 방식이 훨씬 유리하다고 배웁니다.
이는 실제로 이전 세대의 여러 NVIDIA GPU에서 관측된 특성입니다.
하지만 Apple M4에서는 같은 주소에 대한 atomic 덧셈을 하드웨어가 매우 효율적으로 처리하는 것으로 보이며,
오히려 배리어 비용이 상대적으로 더 크게 드러났습니다.

즉 **커널 최적화의 정석은 특정 하드웨어의 비용 비율 위에 세워진 규칙**입니다.
하드웨어가 달라지면 atomic, 공유 메모리, 배리어의 상대 비용도 달라지고 순위가 바뀔 수 있습니다.

그럼에도 v3가 가장 빨랐다는 점은 의미가 있습니다.
"스레드 하나가 충분한 일을 하고, 동기화와 공유를 줄인다"는 방향은 비교적 여러 하드웨어에서 잘 통하는 원칙입니다.
물론 너무 많이 조대화하면 병렬성과 점유율을 잃으므로
워크그룹 수와 스레드당 작업량을 바꿔가며 측정해야 합니다.
정답 확인 방법은 항상 실측입니다.
[26장](/gpu-deep/26-gpu-timing/)에서는 GPU 내부 시간까지 정확하게 측정하는 방법을 살펴봅니다.

:::note[다음 단계 — subgroup 명령]
워프([9장](/gpu/09-gpu-architecture/)) 내부는 원래 같은 명령을 함께 실행하므로
워프 안의 리덕션은 공유 메모리와 배리어 없이 전용 명령으로 수행할 수 있습니다.
WGSL에서는 `enable subgroups;`를 선언하고 `subgroupAdd` 같은 함수를 사용할 수 있습니다.
저자가 wgpu 30.0.0에서 시험했을 때 Metal 백엔드의 일부 변환 경로가 아직 구현되지 않아
이 책에서는 실측을 생략했습니다. wgpu의 subgroup 지원은 집필 시점에도 발전 중입니다.
CUDA에서는 같은 개념을 warp shuffle(`__shfl_down_sync`) 형태로 오래전부터 사용해 왔습니다.
:::

## 정리

- 리덕션은 "병렬로 계산한 뒤 동기화해 하나로 모으는" GPU의 또 다른 기본 패턴입니다
- Apple M4 실측에서 모든 스레드가 atomic을 사용하는 방식은 약 2~4ms,
  공유 메모리 트리는 약 5~15ms, 조대화 후 트리를 사용하는 방식은 약 1~2ms였습니다.
  교과서적인 v2가 가장 느렸습니다
- 스레드 하나의 작업량이 너무 적으면 배리어와 동기화 비용이 지배적일 수 있습니다.
  먼저 레지스터에서 여러 원소를 처리한 뒤 합치는 스레드 조대화가 효과적이었습니다
- 최적화 정석은 하드웨어 비용 구조에 따라 달라집니다.
  atomic이 빠른 GPU도 있고 배리어가 상대적으로 비싼 GPU도 있으므로 이동한 하드웨어에서는 다시 측정해야 합니다
