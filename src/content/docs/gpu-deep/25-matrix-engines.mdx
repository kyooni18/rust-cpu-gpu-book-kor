- 12장의 성능 비교에 이어 벤더 라이브러리를 측정한 결과: 직접 작성한 최선보다 8~11배, 1.47 TFLOP/s
- **행렬 엔진**(Tensor Core, Apple AMX 등)의 하드웨어 구조
- 혼합 정밀도 — [13장](/cpu-deep/13-numbers/)에서 다룬 f16/bf16이 실제로 쓰이는 방식
- Rust에서 행렬 계산 하드웨어를 사용하는 현실적인 선택지
- 왜 이 내용이 필요한가 — 현대 계산 하드웨어의 성능 중심은 행렬 연산 전용 회로로 이동하고 있습니다.
  머신러닝 시대에 "연산 성능이 높다"는 말의 의미를 이해하려면 이 구조를 알아야 합니다

이 장의 실험은 저장소의 `examples/ch25-gemm-lib`입니다.
macOS 전용 예제이며 다른 OS에서는 OpenBLAS 같은 라이브러리로 바꿔 생각할 수 있습니다.

```sh
cd examples
cargo run --release -p ch25-gemm-lib
```

## 12장의 순위표에는 다음 단계가 있습니다

[12장](/gpu/12-cpu-vs-gpu/)에서 n=1024 행렬 곱을 단순 구현의 873밀리초에서
11.3밀리초까지 줄여 약 77배 개선했습니다.
그 장의 마지막에 "실제 행렬 곱은 검증된 라이브러리를 사용하는 것이 맞다"고 적었습니다.
이번에는 그 차이를 실제로 측정합니다.

macOS에 기본으로 포함된 Accelerate 프레임워크는 BLAS 표준의 Apple 구현을 제공합니다.
그 안의 `sgemm`, 즉 f32 행렬 곱을 [20장](/rust-deep/20-unsafe-ub/)에서 본 FFI로 호출해
같은 계산을 수행합니다.

```text
n = 1024 (저자의 Apple M4)
직접 구현 ikj+rayon (12장 CPU 최선): 16.4ms  (  131 GFLOP/s)
직접 구현 GPU blocked (12장 GPU 최선): 11.3ms (  190 GFLOP/s)
Accelerate sgemm                    :  1.5ms  ( 1470 GFLOP/s)
```

초당 **1.47조 번의 부동소수점 연산**입니다.
12장에서 직접 작성한 최선보다 **8~11배** 빠릅니다.
단순 구현과 비교하면 약 600배입니다.
오차는 대략 10^-4 수준에서 직접 구현과 일치합니다.
차이는 [13장](/cpu-deep/13-numbers/)에서 본 f32 연산 순서와 반올림 때문입니다.

이 정도 성능은 소프트웨어 최적화만으로 설명하기 어렵습니다.
Apple CPU 클러스터에는 행렬 연산을 위한 전용 하드웨어가 있으며,
초기 세대에서는 비공개 행렬 코프로세서인 AMX라는 이름으로 알려졌고
M4 세대에서는 Arm 표준의 SME 명령으로 비슷한 능력이 공개됐습니다.
Accelerate는 이런 계열의 하드웨어를 활용하는 것으로 볼 수 있습니다.

## 행렬 엔진 — SIMD 다음 단계

[4장](/cpu/04-simd/)의 SIMD는 1차원으로 나열된 여러 값에 같은 연산을 적용했습니다.
**행렬 엔진**(matrix engine)은 그 다음 단계로,
작은 2차원 타일끼리의 곱셈-누산을 하나의 명령 또는 매우 적은 명령으로 처리하는 전용 회로입니다.

- **NVIDIA Tensor Core** — 워프([9장](/gpu/09-gpu-architecture/)) 단위로 작은 행렬의 곱셈-누산을 처리하는 GPU 내부 연산 유닛입니다
- **Apple AMX / Arm SME** — Apple CPU 클러스터에서 사용할 수 있는 행렬 연산 유닛 계열입니다.
  AMX는 오랫동안 비공개 명령이었고 SME는 Arm 표준으로 공개된 방식입니다
- **Intel AMX** — 서버 CPU에서 타일 레지스터와 행렬 곱 명령을 제공하는 구조입니다

왜 이렇게 빠른지는 이 책에서 배운 두 가지 개념으로 설명할 수 있습니다.

첫째는 **데이터 재사용을 회로 자체가 담당한다는 점**입니다.
[15장](/cpu-deep/15-cache-internals/)의 캐시 블로킹과
[12장](/gpu/12-cpu-vs-gpu/)의 레지스터 블로킹에서는
한 번 읽은 데이터를 여러 계산에 재사용하도록 소프트웨어 구조를 바꿨습니다.
행렬 엔진은 타일 곱에서 필요한 재사용을 **배선과 전용 저장 공간으로 구현**합니다.
피연산자를 한 번 읽으면 내부에서 여러 번 사용합니다.
[10장](/gpu/10-gpu-memory/)의 루프라인 모델에서 말한 산술 강도를
명령어 집합과 하드웨어 수준에서 크게 높이는 셈입니다.

둘째는 **제어 비용이 줄어듭니다**.
하나의 명령이 수백~수천 번의 곱셈과 덧셈에 해당하므로
페치와 디코드([16장](/cpu-deep/16-frontend/)) 비용을 많은 연산에 나눠 부담할 수 있습니다.
[9장](/gpu/09-gpu-architecture/)에서 본 "제어를 줄이고 연산에 하드웨어를 더 사용한다"는 철학의 극단적인 형태입니다.

## 혼합 정밀도 — 13장의 실전 형태

행렬 엔진의 최고 성능 수치는 대부분 **f16이나 bf16**
([13장](/cpu-deep/13-numbers/))을 사용할 때 나옵니다.
값 하나의 폭을 절반으로 줄이면 같은 메모리 대역폭과 하드웨어에서 더 많은 원소를 동시에 처리할 수 있기 때문입니다.

여기서 13장의 원리가 그대로 사용됩니다.
대표적인 행렬 엔진은 **입력은 f16/bf16으로 받고, 누산은 f32로 수행**합니다.
입력의 정밀도를 줄여 처리량을 높이되 여러 곱을 더하는 누산기는 더 넓은 타입을 사용해 오차 누적을 줄입니다.
13장의 Kahan 합계에서 "누산만 더 넓은 타입으로" 처리한 것과 같은 생각입니다.

bf16이 f32와 같은 지수 폭을 유지하는 이유도 여기에서 중요해집니다.
정밀도는 낮지만 표현 가능한 값의 범위가 크게 줄지 않아
학습 과정에서 오버플로나 언더플로를 줄일 수 있습니다.

추론에서는 한 단계 더 나아가 가중치를 int8이나 int4로 줄이는 **양자화**(quantization)가 널리 사용됩니다.
메모리 사용량과 대역폭을 4~8배 줄일 수 있습니다.
현대의 고성능 계산에서는 "필요한 정밀도만큼만 비용을 지불한다"는 접근이 매우 중요합니다.

## 머신러닝이 왜 이런 하드웨어를 만들었을까

행렬 엔진은 "하드웨어는 주요 워크로드를 닮아 간다"는 사실을 보여 주는 최신 사례입니다.
GPU가 화면 렌더링에서 출발했듯이([9장](/gpu/09-gpu-architecture/)),
행렬 엔진은 딥러닝의 폭발적인 수요에서 성장했습니다.
신경망 계산의 많은 부분은 행렬 곱이며,
학습은 어느 정도의 반올림 오차를 허용할 수 있습니다.
"계산의 대부분이 한 종류의 연산이고, 더 낮은 정밀도도 허용된다"는 조건은 전용 하드웨어에 매우 적합합니다.

그 결과 **행렬 곱과 일반 계산 사이의 실효 성능이 한 자릿수 이상 벌어지는 시대**가 됐습니다.
문제를 행렬 곱 형태로 바꿀 수 있다면 머신러닝, 신호 처리, 일부 물리 계산처럼
TFLOP/s급 전용 하드웨어를 사용할 수 있습니다.
그렇지 않은 문제에서는 Part I~IV에서 다룬 일반 CPU/GPU 코어의 수백 GFLOP/s와 메모리 대역폭이 더 중요한 기준이 됩니다.
이 지형을 이해하는 것이 설계의 출발점입니다.

## Rust에서 사용할 수 있는 경로

행렬 연산 성능에 접근하는 대표적인 방법을 정리합니다.

- **OS 또는 벤더 라이브러리를 FFI로 호출** — 이 장의 Accelerate 방식입니다
  ([20장](/rust-deep/20-unsafe-ub/)). Linux에서는 OpenBLAS/BLIS,
  NVIDIA에서는 cuBLAS가 비슷한 역할을 합니다
- **[faer](https://github.com/sarah-quinones/faer-rs)** — 순수 Rust 고성능 선형대수 라이브러리입니다.
  FFI 없이 BLAS 수준의 성능을 목표로 합니다
- **[candle](https://github.com/huggingface/candle) / [burn](https://burn.dev/)** — Rust 머신러닝 프레임워크입니다.
  Metal, CUDA, wgpu 같은 백엔드를 사용해 하드웨어 가속을 활용합니다
- **Metal Performance Shaders / cuBLAS** — GPU 행렬 연산을 위한 벤더 라이브러리입니다.
  [12장](/gpu/12-cpu-vs-gpu/)의 직접 작성한 wgpu 커널보다 훨씬 깊은 최적화를 제공합니다

사용 원칙은 12장과 같습니다. **일반적인 밀집 행렬 곱은 직접 구현하지 않는 편이 좋습니다**.
직접 커널을 작성할 이유는 학습 목적이거나, 기존 라이브러리가 제공하지 않는 특수한 연산 형태나 연산 융합이 필요할 때입니다.

## 정리

- 벤더 라이브러리 행렬 곱은 1.47 TFLOP/s를 기록해 12장의 직접 구현보다 8~11배 빨랐습니다.
  전용 행렬 엔진이 중요한 이유입니다
- 행렬 엔진은 블로킹으로 만들던 데이터 재사용을 하드웨어에 내장하고,
  한 명령에 매우 많은 연산을 넣어 제어 비용을 크게 줄인 SIMD 다음 단계의 구조입니다
- 최고 처리량은 f16/bf16 같은 혼합 정밀도에서 나오는 경우가 많습니다.
  "입력은 좁게, 누산은 넓게"라는 구조는 13장의 수치 안정성 원리와 같습니다
- 문제를 행렬 곱 형태로 표현할 수 있다면 훨씬 높은 성능 영역에 접근할 수 있습니다.
  Rust에서는 FFI, faer, candle/burn 같은 경로를 사용할 수 있습니다
