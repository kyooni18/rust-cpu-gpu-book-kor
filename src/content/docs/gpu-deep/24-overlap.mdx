이 장에서 알 수 있는 것:

- GPU 처리 전체 시간을 결정하는 "동기화 지점"이라는 관점
- 같은 계산량과 같은 전송량에서도 동기화 방식만 바꿔 2.7배 차이가 난 실측
- 파이프라이닝과 더블 버퍼링이라는 설계 패턴
- 실무 GPU 코드가 "먼저 제출하고 나중에 기다리는" 구조를 기본으로 삼는 이유
- 왜 이 내용이 필요한가 — [11장](/gpu/11-wgpu/)과 [12장](/gpu/12-cpu-vs-gpu/)에서는 한 번 계산하고 한 번 기다리는 단발 작업을 다뤘습니다.
  실제 GPU 프로그램은 연속된 작업 흐름을 처리하므로 동기화와 겹치기 설계가 필요합니다

이 장의 실험은 저장소의 `examples/ch24-overlap`입니다.

```sh
cd examples
cargo run --release -p ch24-overlap
```

## 기다림이 전체 흐름을 직렬화합니다

[11장](/gpu/11-wgpu/)에서 GPU 계산 자체는 마이크로초 수준이어도
명령 제출과 완료 대기 왕복은 밀리초까지 커질 수 있다는 것을 봤습니다.
한 번만 실행한다면 이 고정비를 피하기 어렵습니다.
하지만 작업이 **연속해서** 들어온다면 설계를 바꿀 수 있습니다.

데이터를 16개의 청크로 나눠 처리한다고 생각해 보겠습니다.
각 청크는 "계산 → 결과 읽기"의 두 단계로 구성됩니다.
데이터는 이미 GPU에 올라가 있다고 가정합니다.
매번 CPU에서 GPU로 전송해야 한다면 이 장의 원칙은 더 중요해집니다.

가장 단순한 코드는 청크 하나를 제출하고, 완료를 **기다린 뒤**, 결과를 읽고 다음 청크로 넘어갑니다.
그 기다림 동안 CPU는 GPU 결과만 기다리고, GPU는 다음 명령이 아직 오지 않아 놀 수 있습니다.
결국 **CPU와 GPU 중 하나가 자주 대기 상태**가 됩니다.

[3장](/cpu/03-pipeline/)의 파이프라인과 같은 구조입니다.
CPU가 여러 명령 단계를 겹쳐 실행했듯이,
GPU에서도 청크 i를 처리하는 동안 CPU가 청크 i+1의 명령을 준비할 수 있습니다.

## 실험 — 동기화 방식만 바꾸기

16개 청크, 각 4MB에 같은 계산을 적용하고 모든 결과를 읽어옵니다.
계산량과 전송량은 완전히 동일하게 두고 **동기화 위치만** 바꿉니다.

- **(A) 청크마다 동기화** — 각 청크에서 `submit` → `map_async` → `poll(대기)` → 결과 회수를 반복합니다
- **(B) 모두 제출한 뒤 한꺼번에 회수** — 16개 청크의 명령을 기다리지 않고 모두 `submit`하고,
  읽기 매핑도 모두 요청한 뒤 마지막에 **한 번만** 기다려 전체 결과를 회수합니다

저자의 Apple M4 실측입니다.

```text
(A) 청크마다 동기화      :  30~34ms
(B) 모두 제출→한꺼번에 회수: 약 11.8ms
```

**약 2.7배 차이**입니다.
계산도 데이터도 바뀌지 않았고 CPU가 GPU를 기다린 횟수만 16번에서 1번으로 줄었습니다.

(B)가 빨라지는 이유는 크게 두 가지입니다.
첫째, **GPU 작업 큐가 계속 채워져 있습니다**.
(A)에서는 각 청크가 끝날 때마다 다음 명령을 기다리는 빈틈이 생깁니다.
(B)에서는 다음 작업이 이미 큐에 있으므로 GPU가 청크 사이를 거의 끊김 없이 넘어갑니다.

둘째, CPU가 다음 명령을 기록하는 시간이 GPU의 현재 작업과 **자연스럽게 겹칩니다**.
이번 예제에서는 결과 집계를 마지막에 한꺼번에 하지만,
핵심은 특별한 API가 아니라 "가능한 빨리 제출하고, 정말 필요한 순간까지 기다리지 않는다"는 구조입니다.

## 설계 패턴으로 정리하기

이 원리를 실무에서 쓰기 좋은 형태로 정리해 보겠습니다.

**기본은 먼저 제출하기입니다.** `queue.submit`은 비동기입니다
([11장](/gpu/11-wgpu/)). 결과가 실제로 필요한 순간까지 기다리지 않는 것이 중요합니다.
프로그램에서 기다리는 위치, 즉 동기화 지점을 세어 보는 것이 GPU 성능 분석의 좋은 출발점입니다.
[26장](/gpu-deep/26-gpu-timing/)에서 이를 측정하는 도구를 살펴봅니다.

**더블 버퍼링을 사용합니다.** 모든 청크의 버퍼를 한꺼번에 만들 여유가 없다면 두 세트만 있어도 됩니다.
GPU가 버퍼 세트 1을 처리하는 동안 CPU가 버퍼 세트 2에 다음 데이터를 준비하고,
작업이 끝날 때마다 두 세트를 교대로 사용합니다.
이 패턴을 **더블 버퍼링**(double buffering)이라고 부릅니다.
화면 렌더링의 프런트/백 버퍼부터 과학 계산까지 매우 널리 사용됩니다.
[18장](/rust-deep/18-allocators/)의 버퍼 재사용과 같은 원리로,
매번 새로 할당하는 대신 기존 저장 공간을 반복해서 사용합니다.

**연속된 GPU 작업은 GPU 안에서 연결합니다.**
[10장](/gpu/10-gpu-memory/)에서 본 원칙입니다.
계산 A 뒤에 계산 B가 이어진다면 A의 결과를 CPU로 읽어온 뒤 다시 B 입력으로 업로드하지 말고,
A의 출력 버퍼를 B의 입력으로 그대로 연결합니다.
바인드 그룹을 바꾸는 정도로 연결할 수 있으며,
CPU로 읽어오는 작업은 정말 필요한 마지막 단계에서 한 번만 수행합니다.

**CPU의 비동기 실행과도 합칠 수 있습니다.**
[19장](/rust-deep/19-async/)의 async와 결합할 때 `map_async` 완료를 Future로 감싸면
GPU 완료 대기도 I/O 대기처럼 다중화할 수 있습니다.
기본적인 연결 방법은 콜백에서 채널의 송신 측을 깨우고, 수신 측을 `await`하는 형태입니다.
wgpu의 공식 예제에서도 비슷한 패턴을 볼 수 있습니다.
tokio 워커 안에서 블로킹 `poll(wait)`를 호출하지 않는다는
[19장](/rust-deep/19-async/)의 규칙도 그대로 적용됩니다.

:::note[PCIe 기반 외장 GPU에서는 효과가 더 커질 수 있습니다]
이 실험은 유니파이드 메모리([10장](/gpu/10-gpu-memory/))를 사용하는 Mac에서 진행했기 때문에
주로 동기화 사이의 빈틈을 줄인 효과를 측정했습니다.
PCIe로 연결된 외장 GPU에서는 실제 데이터 전송 시간이 더 크기 때문에
"청크 i를 계산하는 동안 청크 i+1을 전송"하는 겹치기의 효과가 더 커질 수 있습니다.
CUDA에서는 스트림과 전용 복사 엔진을 통해 이런 패턴을 명시적으로 지원합니다.
원칙은 같습니다. **직렬로 보이는 처리에서 서로 독립적인 부분을 찾아 겹칩니다**.
:::

## 정리

- GPU 처리 시간은 계산량과 전송량뿐 아니라 동기화 지점의 수에도 크게 좌우됩니다.
  실험에서는 동기화를 16번에서 1번으로 줄였을 뿐인데 약 2.7배 빨라졌습니다
- 기본 원칙은 "빨리 제출하고 늦게 기다리기"입니다. `submit` 자체는 기다리지 않으며 결과는 필요할 때만 회수합니다
- 메모리를 더 사용해 작업을 겹치는 대표 패턴이 더블 버퍼링입니다.
  읽기 자체를 줄이는 방법은 중간 결과를 GPU에 둔 채 다음 커널로 연결하는 것입니다
- 이 원리는 3장의 파이프라인, 19장의 비동기 I/O와 같은 구조입니다.
  **기다림을 겹쳐 숨기는 것**은 이 책 전체를 관통하는 패턴입니다

다음 장에서는 GPU 계산 성능의 중심에 있는 행렬 엔진과 혼합 정밀도를 살펴봅니다.
직접 작성한 커널의 한계를 넘어 하드웨어와 라이브러리가 제공하는 성능을 측정합니다.
