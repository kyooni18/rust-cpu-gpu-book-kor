## 사용자 공간과 커널 공간

운영체제는 애플리케이션이 실행되는 **사용자 공간**과 커널이 실행되는 **커널 공간**을
CPU의 특권 레벨로 분리합니다.
파일을 읽고, 스레드를 만들고, 하드웨어나 다른 프로세스와 관련된 작업을 하려면
애플리케이션이 **시스템 콜**(system call)을 통해 커널에 요청해야 합니다.

이 보호 경계에는 비용이 있습니다.
거의 아무 일도 하지 않는 `getpid` 시스템 콜과 일반 함수 호출을 비교해 보겠습니다.

<RustPlay code={syscall} mode="release" title="일반 함수 호출과 시스템 콜 비교" />

저자가 Playground에서 측정했을 때 일반 함수 호출은 약 1.9나노초,
`getpid`는 **약 222.6나노초로 약 120배**였습니다.

차이는 여러 요소에서 생깁니다.
CPU 특권 수준을 바꾸는 전용 명령, 레지스터 저장과 복원,
그리고 최근 CPU 취약점 완화 기법으로 인해 사용자와 커널 주소 공간을 더 엄격하게 분리하는 비용 등이 포함됩니다.
이 과정에는 [14장](/cpu-deep/14-virtual-memory/)의 페이지 테이블과 TLB도 관련됩니다.

눈에 잘 보이지 않는 비용도 있습니다.
커널 코드를 실행하면 **캐시와 TLB 상태가 바뀌어**
([2장](/cpu/02-memory-hierarchy/), [14장](/cpu-deep/14-virtual-memory/))
사용자 코드로 돌아온 직후에도 약간의 성능 손실이 생길 수 있습니다.

이 수치에서 I/O 설계의 첫 번째 원칙이 나옵니다. **배치 처리**입니다.
1바이트마다 `write`를 호출하면 시스템 콜 비용을 매 바이트마다 지불합니다.
64KB를 한 번에 쓰면 같은 경계 비용을 훨씬 많은 데이터에 나눠 부담할 수 있습니다.
Rust의 `BufReader`와 `BufWriter`가 바로 이런 배치화를 자동으로 수행합니다.
"파일 I/O에는 버퍼를 사용하라"는 규칙에 하드웨어적인 이유가 있습니다.

`Instant::now()`처럼 매우 자주 호출되는 작업이 비교적 저렴한 이유도 같은 원리입니다.
Linux에서는 vDSO를 통해 커널이 일부 시간 정보를 사용자 공간에서 직접 읽을 수 있게 제공하여
매번 시스템 콜을 하지 않도록 합니다.
**자주 사용하는 기능은 가능하면 경계를 넘지 않게 만든다**는 같은 원칙입니다.

## 스레드 간 왕복 비용 — 컨텍스트 스위치

스레드 전환, 즉 **컨텍스트 스위치**(context switch)는 시스템 콜보다 더 복합적인 비용을 가질 수 있습니다.
두 스레드가 채널을 통해 값을 주고받으며 서로를 깨우는 실험으로 측정해 보겠습니다.
한 번 왕복하려면 최소 두 번의 "상대를 깨우고 자신은 기다리기"가 필요합니다.

<RustPlay code={ctxSwitch} mode="release" title="스레드 사이 왕복 비용 측정" />

저자가 Playground의 2코어 환경에서 측정했을 때 **왕복 한 번에 약 18마이크로초**였습니다.

이 값은 순수한 "컨텍스트 스위치 명령 하나"의 비용은 아닙니다.
채널 송수신, futex 같은 커널 대기/깨우기 시스템 콜, 스케줄러 실행,
필요하다면 레지스터와 스택 상태 전환, 그리고 캐시와 TLB의 재워밍업까지 포함한
**스레드 사이 동기화 한 번의 실제 총비용**입니다.
실무에서는 이런 전체 비용이 더 중요한 기준입니다.

이 값을 [19장](/rust-deep/19-async/)의 async 태스크와 비교해 보세요.
async 태스크 전환은 사용자 공간에서 함수 호출과 큐 조작 정도로 끝나며 서브마이크로초 수준일 수 있지만,
OS 스레드끼리의 전환은 수십 마이크로초까지 커질 수 있습니다.
"대기 중인 작업을 OS 스레드 하나씩으로 표현하지 않고 사용자 공간에서 다중화한다"는
async 런타임의 존재 이유가 여기에서 드러납니다.

[5장](/cpu/05-multicore/)의 Rayon이 스레드를 매번 만들지 않고 풀로 재사용하는 이유도 같습니다.
스레드 생성 비용과 전환 비용을 계속 지불하지 않기 위해서입니다.

## 파일 I/O와 페이지 캐시

파일 I/O를 단순히 "매번 디스크를 읽는 작업"이라고 생각하면 실제 동작을 놓치게 됩니다.
OS는 최근 읽고 쓴 파일 내용을 메모리에 저장하는 **페이지 캐시**(page cache)를 사용합니다.
이는 [14장](/cpu-deep/14-virtual-memory/)의 페이지 메커니즘을 활용한 구조입니다.
두 번째 이후의 접근은 실제 저장 장치가 아니라 메모리에서 처리될 수 있습니다.

페이지 캐시에 이미 올라온 64MB 파일을 읽는 두 방법을 비교합니다.
일반적인 `fs::read`와 [14장](/cpu-deep/14-virtual-memory/)에서 소개한 `mmap`입니다.
`mmap` 호출은 [20장](/rust-deep/20-unsafe-ub/)의 FFI와 저수준 OS API를 사용하는 예이기도 합니다.

<RustPlay code={fileIo} mode="release" title="캐시된 파일에서 fs::read와 mmap 비교" />

저자의 Playground 실측입니다.

```text
쓰기(64MB)     : 92ms  (페이지 캐시에 받아들이는 시간. 실제 디스크 반영은 비동기)
fs::read 1회차 : 59ms
fs::read 2회차 : 59ms
mmap + 순회    : 15ms   (3.9배)
```

`fs::read`의 59밀리초에는 64MB 힙 버퍼 할당과 첫 접근 비용
([18장](/rust-deep/18-allocators/), [14장](/cpu-deep/14-virtual-memory/)의 페이지 폴트),
그리고 **페이지 캐시에서 사용자 버퍼로 데이터를 복사하는 비용**이 포함됩니다.

반면 `mmap`은 페이지 캐시에 있는 파일 페이지를 프로세스의 가상 주소 공간에 직접 매핑합니다.
별도의 64MB 사용자 버퍼 할당과 전체 복사가 필요하지 않습니다.
대신 파일 페이지를 처음 만질 때 페이지 폴트가 발생할 수 있습니다.
이런 차이를 합치면 실험에서 약 3.9배 차이가 나타났습니다.

`mmap`이 항상 좋은 것은 아닙니다.
페이지 폴트가 접근 시점에 발생할 수 있고,
I/O 오류가 일반적인 함수 반환값이 아니라 SIGBUS 같은 시그널 형태로 나타날 수 있으며,
작은 파일에서는 매핑 준비 비용이 더 클 수 있습니다.
따라서 대형 읽기 중심 파일에 특히 잘 맞습니다.
Rust에서는 [memmap2](https://github.com/RazrFalcon/memmap2-rs) 크레이트가 널리 사용됩니다.

## 시스템 콜을 줄이는 현대 I/O

이 장의 실험들은 모두 경계를 넘을 때 비용이 생긴다는 것을 보여 줍니다.
현대의 고성능 I/O는 이 경계 왕복 횟수 자체를 줄이는 방향으로 발전하고 있습니다.

대표적인 예가 Linux의 **io_uring**입니다.
애플리케이션과 커널이 제출 큐와 완료 큐라는 두 개의 링 버퍼를 공유 메모리에 두고,
많은 I/O 요청을 **소수의 시스템 콜로 묶어서** 제출하고 완료 결과도 한꺼번에 회수합니다.
설정에 따라 커널 측 전용 스레드가 큐를 감시하게 만들어 제출 시스템 콜 자체도 크게 줄일 수 있습니다.

[24장](/gpu-deep/24-overlap/)의 GPU 명령 큐와 매우 비슷한 구조입니다.
"요청 하나를 보내고 기다린 뒤 다음 요청"이 아니라
"여러 요청을 먼저 쌓고 나중에 완료를 모아서 확인"합니다.
Rust에서는 tokio-uring이나 glommio 같은 런타임이 이런 기능을 활용합니다.

커널 바이패스와 DPDK 같은 더 극단적인 기술도 있지만 방향은 같습니다.
**자주 넘나드는 경계는 설계로 줄이거나 없앱니다**.
함수 호출을 인라이닝으로 없애고([6장](/rust-opt/06-compiler/)),
FFI 경계는 큰 작업 단위로 넘기고([20장](/rust-deep/20-unsafe-ub/)),
GPU 명령은 묶어서 제출하고([24장](/gpu-deep/24-overlap/)),
OS I/O도 배치 처리합니다.
이 책에서 반복해서 나타난 같은 원칙입니다.

## 정리

- 시스템 콜은 일반 함수 호출보다 약 120배 비쌌습니다. 실측 `getpid`는 약 222나노초였습니다.
  I/O에서는 배치 처리가 중요하며 `BufReader`/`BufWriter`가 이를 자동화합니다
- 스레드 사이 깨우기 왕복은 약 18마이크로초였습니다.
  async 태스크 전환이 더 가벼운 이유는 대부분의 작업을 사용자 공간에서 처리하기 때문입니다
- 파일 I/O는 페이지 캐시를 통해 처리됩니다. `mmap`은 별도 복사를 없애 실험에서 약 3.9배 빨랐습니다.
  다만 큰 읽기 중심 파일처럼 적합한 용도에서 사용하는 편이 좋습니다
- io_uring은 요청을 큐에 쌓고 한꺼번에 처리해 시스템 콜 횟수를 줄입니다.
  **자주 넘는 경계는 설계로 줄인다**는 원칙이 OS 계층에서도 그대로 적용됩니다

마지막 장에서는 지금까지의 지식을 실제 성능 엔지니어링 과정에 묶습니다.
지연 시간 분포, 성능 회귀 방지, 그리고 이 책 전체를 관통하는 원칙을 정리합니다.
