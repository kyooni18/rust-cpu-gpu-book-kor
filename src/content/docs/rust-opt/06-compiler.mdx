이 장에서 알 수 있는 것:

- Rust 코드가 기계어가 되기까지 거치는 변환 단계와 rustc·LLVM의 역할 분담
- 컴파일러 최적화의 실체와 작은 변환이 연쇄되며 큰 차이를 만드는 원리
- 인라이닝이 다른 최적화의 출발점이 되는 이유와 실제 측정 결과
- 1장에서 "1억 번의 루프가 순식간에 끝난" 이유
- `opt-level`, LTO, `codegen-units` 같은 빌드 설정의 사용법

## 컴파일러 내부에서 일어나는 일

`cargo build`를 실행하면 코드는 여러 단계를 거쳐 기계어로 변환됩니다.
다음 그림이 전체 흐름을 보여 줍니다.

```mermaid
flowchart LR
    src["소스 코드"] --> hir["HIR"]
    subgraph rustc ["rustc (Rust 고유 처리)"]
        hir --> mir["MIR"] --> mopt["MIR 최적화·단형화"]
    end
    subgraph llvm ["LLVM (최적화와 코드 생성)"]
        ir["LLVM IR"] --> opt["최적화 패스"] --> mc["기계어"]
    end
    mopt --> ir
    mc --> bin["링크 → 실행 파일"]
```

중간에 등장하는 HIR, MIR, LLVM IR은 **중간 표현**(intermediate representation, IR)이라고 부르는
컴파일러 내부용 프로그램 표현입니다. 단계가 진행될수록 표현을 단순하게 만들고,
각 단계에서 다루기 좋은 형태로 필요한 처리를 수행합니다.

- **rustc**는 구문 분석, 타입 검사, 빌림 검사 같은 Rust 고유의 검사를 수행하고
  코드를 MIR(mid-level IR)이라는 단순화된 표현으로 변환합니다.
  MIR 단계에서도 일부 최적화가 이루어지며, 제네릭 코드를 구체적인 타입별 구현으로
  펼치는 **단형화**(monomorphization)도 이 과정에서 이루어집니다
  ([7장](/rust-opt/07-zero-cost/)에서 자세히 다룹니다)
- **LLVM**은 여러 언어가 함께 사용하는 최적화·코드 생성 기반입니다.
  C/C++의 Clang과 Swift도 LLVM을 사용합니다.
  기계어 수준의 성능에 직접 영향을 주는 최적화 대부분은 LLVM이 담당합니다

LLVM IR은 실제 형태를 보는 것이 이해하기 가장 빠릅니다. 1장의 `add` 함수는 다음처럼 표현됩니다.

```llvm
define i32 @add(i32 %a, i32 %b) {
  %_0 = add i32 %b, %a
  ret i32 %_0
}
```

타입 정보가 붙어 있고 레지스터가 무한히 있다고 가정하는 가상의 어셈블리와 비슷합니다.
LLVM에는 수백 개의 최적화 패스가 있으며 이 IR을 계속 변환합니다.

## 최적화는 단순한 변환의 연쇄입니다

컴파일러 최적화를 하나씩 보면 대부분 단순한 코드 변환입니다.
대표적인 예는 다음과 같습니다.

- **상수 폴딩**(constant folding) — `60 * 60 * 24` 같은 식을 컴파일 시점에 계산해 `86400`으로 바꿉니다
- **죽은 코드 제거**(dead code elimination) — 결과가 어디에서도 사용되지 않는 계산을 삭제합니다
- **공통 부분식 제거**(common subexpression elimination) — 같은 계산이 여러 번 나오면 한 번만 계산하고 결과를 재사용합니다
- **루프 불변 코드 이동**(loop-invariant code motion) — 루프 안에서 매번 같은 결과가 나오는 계산을 루프 밖으로 옮깁니다
- **루프 언롤링**(loop unrolling) — 루프 본문을 여러 번 펼쳐 분기 횟수를 줄이고
  ILP(3장)와 SIMD화(4장)가 적용될 여지를 만듭니다

하나하나는 단순한 변환입니다. 하지만 이런 패스가 여러 차례 적용되고,
**한 변환이 다음 변환이 가능한 조건을 만들어 주는** 연쇄가 일어나면
최종 코드는 원래 모습과 크게 달라질 수 있습니다.

## 인라이닝 — 다른 최적화의 시작점

이 연쇄의 출발점이 되는 대표적인 변환이 **인라이닝**(inlining)입니다.
함수 호출을 실제 함수 본문으로 바꾸는 최적화입니다.

왜 출발점일까요? 컴파일러 관점에서 함수 호출은 내부가 보이지 않는 경계가 될 수 있습니다.
그 경계를 넘어선 최적화는 어렵습니다. 인라이닝으로 경계를 없애면
호출한 코드와 함수 본문이 하나의 연속된 코드가 되고,
앞에서 살펴본 다른 최적화 패스들이 모두 적용될 수 있습니다.

효과를 직접 측정해 보겠습니다. "두 수를 더하는 함수"를 1억 번 호출하는 루프를
인라이닝을 금지한 경우와 컴파일러의 판단에 맡긴 경우로 비교합니다.

<RustPlay code={inline} mode="release" title="작은 함수를 1억 번 호출하기: 인라이닝 여부 비교" />

저자가 Playground에서 측정했을 때 `#[inline(never)]` 버전은 약 155밀리초,
컴파일러에 맡긴 버전은 **약 30나노초**였습니다. 약 500만 배 차이입니다.
함수 호출 한 번의 비용 자체는 수 나노초 수준입니다.
이 큰 차이는 호출 비용 때문이 아니라, 인라이닝이 막히면서 뒤이어 적용될
최적화의 연쇄 전체가 끊어졌기 때문에 생깁니다.

30나노초라는 값이 익숙하게 느껴질 수도 있습니다.
1장에서 release 빌드에서 루프가 사라졌던 실험과 같은 현상입니다.
인라이닝으로 함수 내부가 루프 안에 드러나자 LLVM은 루프 전체를 분석할 수 있게 되었고,
결과를 닫힌 형태의 수식으로 바꾸었습니다.

## 1장에서 루프가 사라진 이유

그 변환 결과를 실제로 확인해 보겠습니다.
0부터 `n-1`까지 더하는 루프를 release 빌드했을 때의 x86-64 어셈블리입니다.

```rust
pub fn sum_to(n: u64) -> u64 {
    let mut sum: u64 = 0;
    let mut i: u64 = 0;
    while i < n {
        sum = sum.wrapping_add(i);
        i += 1;
    }
    sum
}
```

```asm
sum_to:
	test	rdi, rdi
	je	.LBB0_1
	lea	rax, [rdi - 1]
	lea	rcx, [rdi - 2]
	mul	rcx
	shld	rdx, rax, 63
	lea	rax, [rdi + rdx]
	dec	rax
	ret
.LBB0_1:
	xor	eax, eax
	ret
```

루프가 없습니다. `mul`(곱셈)과 `shld`(시프트)를 사용해
등차수열의 합 공식 n(n−1)/2를 계산합니다.
1억 번 반복한다고 작성한 코드가 약 10개의 명령어로 바뀐 셈입니다.
LLVM의 루프 분석은 루프가 계산하는 값을 수식 형태로 인식할 수 있으며,
가능한 경우에는 이렇게 루프 자체를 제거합니다.

반면 `#[inline(never)]` 버전은 함수 호출이라는 경계가 그대로 남습니다.
따라서 "1억 번 호출해서 더한다"는 작업을 실제로 수행해야 합니다.
155밀리초와 수십 나노초의 차이는 최적화 연쇄가 이어졌는지 여부에서 생깁니다.

`#[inline]` 계열 속성은 컴파일러에 주는 강한 힌트이지 언어 사양이 보장하는 명령은 아닙니다.
현재 rustc에서는 일반적으로 의도대로 반영됩니다.

실무에서는 다음 정도의 기준을 기억하면 충분합니다.

- 같은 크레이트 안의 함수와 제네릭 함수는 컴파일러가 적절히 자동 인라이닝하는 경우가 많습니다.
  기본적으로 컴파일러에 맡겨도 됩니다
- 다른 크레이트에 공개하는 작은 함수에 `#[inline]`을 붙이면 호출하는 크레이트에서도
  인라이닝 후보로 다룰 수 있습니다. 뒤에서 설명할 LTO도 이 경계를 넘는 데 도움이 됩니다
- `#[inline(always)]`를 과하게 사용하면 코드 크기가 커지고 명령어 캐시를 압박해
  오히려 느려질 수 있습니다. 최종 판단은 측정으로 해야 합니다

## 빌드 설정이 바꾸는 것

컴파일러가 어느 정도까지 최적화할지는 Cargo 설정으로 제어할 수 있습니다.
주요 항목은 다음과 같습니다.

- **opt-level** — 최적화 수준입니다. `0`은 최적화 없음(debug 빌드 기본값),
  `3`은 최대 최적화(release 빌드 기본값)입니다. `s`와 `z`는 코드 크기를 우선합니다
- **codegen-units** — 크레이트를 몇 부분으로 나누어 병렬 컴파일할지 정합니다.
  release의 기본값은 16입니다. `1`로 설정하면 빌드는 느려지지만
  최적화가 크레이트 전체를 더 넓게 볼 수 있습니다
- **lto**(link-time optimization) — 링크 시점에 크레이트 경계를 넘어
  최적화, 특히 인라이닝을 수행합니다. `"thin"`은 효과와 빌드 시간의 균형이 좋은 선택입니다
- **panic** — `"abort"`로 설정하면 패닉 시 스택 되감기 처리가 사라져
  코드 크기가 조금 줄고 약간 빨라질 수 있습니다. 대신 패닉을 잡을 수 없습니다

성능을 우선할 때 자주 사용하는 설정은 다음과 같습니다.

```toml
[profile.release]
lto = "thin"
codegen-units = 1
```

여기에 [4장](/cpu/04-simd/)의 `target-cpu=native`를 함께 쓰는 것은
로컬에서 실행하는 계산 중심 프로그램에서 자주 사용하는 설정입니다.
모두 빌드 시간과 맞바꾸는 선택이므로 실제 효과는 측정해서 확인해야 합니다
([8장](/rust-opt/08-measure/)).

한 단계 더 나아간 방법으로 **PGO**(profile-guided optimization)가 있습니다.
프로그램을 한 번 실행해 "어떤 분기가 자주 실행되는지" 같은 프로파일 정보를 모은 다음,
그 정보를 컴파일러에 제공해 코드 배치와 최적화 판단에 실제 실행 패턴을 반영하는 방식입니다.
적용 과정이 복잡해 모든 프로젝트에 적합한 것은 아니므로 여기서는 개념만 소개합니다.

:::note[release 빌드에서는 속도 외의 동작도 달라집니다]
debug 빌드에서는 정수 오버플로를 검사하고 오버플로가 발생하면 패닉합니다.
release 빌드에서는 기본적으로 이 검사가 제거되고 값이 순환합니다(wrapping).
이 책의 스니펫에서 `wrapping_add`를 사용해 온 이유는
"순환하는 동작이 의도된 것"임을 명시하기 위해서입니다.
:::

## 컴파일러와 역할 나누기

마지막으로 이 장의 내용을 실제 코드 작성과 연결해 보겠습니다.

LLVM 최적화를 방해하는 것은 내부가 보이지 않는 경계입니다.
`#[inline(never)]`는 의도적으로 만든 예지만, 실무에서는
FFI(다른 언어 함수) 호출이나 [7장](/rust-opt/07-zero-cost/)에서 다룰
동적 디스패치도 비슷한 성질을 가질 수 있습니다.

반대로 Rust이기 때문에 최적화하기 쉬운 부분도 있습니다.
여러 참조가 같은 메모리를 가리키는 것을 **에일리어싱**(aliasing)이라고 부릅니다.
Rust에서는 가변 참조 `&mut T`가 동시에 하나만 존재할 수 있으므로,
컴파일러는 "이 `&mut`가 살아 있는 동안 같은 메모리를 다른 경로에서 읽거나 쓰지 않는다"는
정보를 LLVM에 전달할 수 있습니다.
에일리어싱 가능성을 더 정확하게 제한할 수 있으므로 LLVM은 메모리 접근 순서를 바꾸거나
벡터화하는 최적화를 더 안전하게 적용할 수 있습니다.
C/C++에서는 프로그래머가 주의해서 지켜야 했던 일부 전제를
Rust에서는 타입 시스템이 기계적으로 보장해 주는 셈입니다.

다만 컴파일러가 최적화할 수 있는 범위는 어디까지나 "작성된 코드 안"입니다.
O(n²) 알고리즘을 O(n log n) 알고리즘으로 바꾸는 식의 설계 변화까지 해 주지는 않습니다.
알고리즘과 자료구조를 선택하는 것은 사람의 역할이고,
작성한 구현을 기계어 수준에서 다듬는 것은 컴파일러의 역할이라고 생각하면 됩니다.

## 정리

- rustc는 Rust 고유의 검사와 MIR 변환·단형화를 담당하고,
  기계어 수준의 최적화 대부분은 LLVM이 LLVM IR에서 수행합니다
- 최적화는 단순한 변환 패스의 연쇄입니다. 인라이닝이 함수 경계를 열어
  다른 최적화에 기회를 만들어 줍니다. 실험에서는 약 500만 배 차이가 나타났습니다
- 1장의 루프가 사라진 이유는 LLVM이 루프를 수식으로 인식해
  닫힌 형태의 계산으로 바꾸었기 때문입니다
- 성능을 우선한다면 `lto = "thin"`, `codegen-units = 1`, 필요에 따라
  `target-cpu=native`를 고려할 수 있습니다. 효과는 반드시 측정으로 확인해야 합니다

다음 장에서는 이런 최적화 능력을 전제로 Rust의 대표적인 특징인
"제로 비용 추상화"가 실제로 어디까지 성립하는지 확인합니다.
이터레이터, 경계 검사, `dyn Trait` 같은 추상화가 만드는 비용을
어셈블리와 실제 측정 결과를 통해 살펴보겠습니다.
