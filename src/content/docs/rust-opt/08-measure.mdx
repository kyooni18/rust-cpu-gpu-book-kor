이 장에서 알 수 있는 것:

- 성능 측정에 쓰는 네 가지 도구의 역할: 벤치마크, 프로파일러,
  하드웨어 카운터, 어셈블리
- `criterion`으로 벤치마크를 작성하고 결과를 읽는 방법
- 측정을 무의미하게 만드는 함정: 최적화로 인한 코드 제거, 지연 평가, debug 빌드
- 최적화를 진행할 때의 우선순위

## 왜 먼저 측정해야 할까

지금까지 직감이 잘 맞지 않는 사례를 여러 번 봤습니다.
읽기 횟수를 1/8로 줄여도 빨라지지 않았고(2장), 데이터 순서만 바꿔 10배 차이가 났으며(3장),
함수 호출 여부 하나가 500만 배 차이로 이어지기도 했습니다(6장).
현대 CPU와 컴파일러의 동작은 복잡해서
**어디가 느릴지 추측하는 일은 경험이 많아도 자주 틀립니다**.

그래서 절차는 항상 다음과 같습니다.

1. 측정해서 느린 지점을 찾습니다
2. 가설을 세우고 수정합니다
3. 다시 측정해서 효과를 확인합니다. 효과가 없으면 되돌립니다

이 장에서는 이 과정을 위한 도구를 역할별로 정리합니다.
"어디가 느린지" 찾는 도구가 프로파일러,
"얼마나 빨라졌는지" 확인하는 도구가 벤치마크,
"왜 느린지" 파악하는 도구가 하드웨어 카운터,
"어떤 기계어로 바뀌었는지" 확인하는 방법이 어셈블리 분석입니다.

## 벤치마크 — criterion

**벤치마크**(benchmark), 즉 특정 처리의 성능을 통계적으로 측정할 때는
[criterion](https://github.com/bheisler/criterion.rs) 크레이트를 많이 사용합니다.
7장의 "Vec를 만드는 세 가지 방식"을 벤치마크로 작성하면 다음과 같습니다.

```toml
# Cargo.toml
[dev-dependencies]
criterion = "=0.8.2"

[[bench]]
name = "build_vec"
harness = false
```

`harness = false`는 표준 테스트 러너 대신 criterion이 직접 벤치마크 실행을 관리하도록 하는 설정입니다.

```rust
// benches/build_vec.rs
use criterion::{Criterion, criterion_group, criterion_main};
use std::hint::black_box;

fn build_collect(src: &[u32]) -> Vec<u64> {
    src.iter().map(|&v| v as u64 * 2).collect()
}

fn bench_build(c: &mut Criterion) {
    let src: Vec<u32> = (0..1_000_000).collect();
    // iter_with_large_drop: 반환값(Vec) 해제 시간은 측정에서 제외합니다
    c.bench_function("collect", |b| {
        b.iter_with_large_drop(|| build_collect(black_box(&src)))
    });
    // push 버전과 with_capacity 버전도 같은 방식으로 등록합니다
}

criterion_group!(benches, bench_build);
criterion_main!(benches);
```

`b.iter_with_large_drop(...)` 부분이 실제 측정 대상입니다.
전달한 클로저를 여러 번 실행해 통계를 냅니다. 기본 형태는 `b.iter`이지만,
여기서는 생성한 `Vec`의 해제 시간을 측정에서 빼기 위해 이 메서드를 사용합니다.
마지막의 `criterion_group!`과 `criterion_main!`은 벤치마크 함수를 등록하고
`main` 함수를 생성하는 매크로입니다.

`cargo bench`로 실행합니다. 다음은 저자의 Mac(Apple M4)에서 얻은 결과입니다.

```text
push                    time:   [975.69 µs 988.17 µs 1.0028 ms]
with_capacity           time:   [537.33 µs 541.88 µs 546.73 µs]
collect                 time:   [110.12 µs 110.56 µs 111.04 µs]
```

세 숫자는 [하한 추정값 상한]으로, 추정값의 흔들림 범위인 95% 신뢰구간을 뜻합니다.
criterion은 자동으로 워밍업을 수행하고 여러 번 실행한 결과로 통계를 내며,
이전 실행과 비교해 개선인지 악화인지도 알려 줍니다.
한 번만 `Instant`로 재는 방식보다 일시적인 흔들림에 덜 속는 것이 장점입니다.

같은 비교를 Playground의 공유 x86-64 환경에서 수행한 7장과는
성능 배율이 꽤 다릅니다. **성능 수치는 실행 환경에 크게 의존합니다**.
이 책이 계속 "저자의 측정에서는"이라고 적는 이유도 여기에 있습니다.
실제 프로젝트에서는 자신의 환경에서 측정한 결과가 기준입니다.

## 함정 — 측정했다고 생각했지만 실제로는 측정하지 못한 경우

벤치마크에서 가장 위험한 것은 잘못된 수치를 그럴듯하게 믿는 것입니다.
대표적인 함정을 세 가지 살펴보겠습니다.

**첫 번째: 컴파일러가 측정 대상 코드를 없앱니다.**
7장의 `collect` 실험처럼 결과가 사용되지 않는 계산은
죽은 코드 제거(6장)로 사라질 수 있습니다.
이를 막기 위한 도구가 `std::hint::black_box`입니다.
값을 넘기면 컴파일러가 "이 값은 사용된다"고 가정하게 해
코드 제거와 상수 폴딩을 억제합니다.
criterion의 `b.iter(...)`는 반환값을 자동으로 `black_box`에 통과시키지만,
입력도 `black_box(&src)`처럼 감싸 두면 컴파일러가 입력을 상수로 보고
컴파일 시점에 계산해 버리는 상황까지 줄일 수 있습니다.

**두 번째: 지연 평가입니다.** Rust의 이터레이터는 실제로 소비되기 전까지
계산을 시작하지 않습니다. 직접 확인해 보겠습니다.

<RustPlay code={lazy} mode="release" title="무거운 처리를 map했는데 왜 순식간에 끝날까?" />

저자가 Playground에서 측정했을 때 `map`만 만든 경우는 약 110나노초,
`sum`까지 실행한 경우는 약 116밀리초였습니다. **약 100만 배 차이**입니다.
첫 번째 경우 `slow_square`는 한 번도 호출되지 않습니다.
더 나아가 사용되지 않는 이터레이터 자체가 최적화로 사라질 가능성도 높기 때문에,
실제로 측정된 것은 시간 측정 오버헤드 정도일 수 있습니다.
"여기까지 실행한 시간을 재겠다"고 생각했지만 아무 작업도 실행되지 않은 사고는
비동기 `Future`에서도 생깁니다. `Future` 역시 `.await`되기 전에는 실제로 실행되지 않습니다.

**세 번째: debug 빌드에서 측정합니다.** 1장에서 확인했듯이 debug 빌드의 성능은
최적화된 실제 실행과 크게 다릅니다. `cargo bench`와 `cargo run --release`는
최적화가 켜지지만, `cargo run`과 `cargo test`는 기본적으로 debug 빌드입니다.

그 밖에도 노트북의 전원 설정, 발열에 따른 클록 변화,
다른 프로세스의 부하가 결과를 흔들 수 있습니다.
몇 번 반복해서 같은 경향이 유지되는지 확인하는 것만으로도 많은 실수를 줄일 수 있습니다.

## 프로파일러 — 어디가 느린지 찾기

벤치마크는 "이 함수의 성능"을 재는 도구였습니다.
프로그램 전체에서 "어디에 시간이 쓰이는지" 찾으려면
**프로파일러**(profiler)를 사용합니다.
실행 중인 프로그램을 높은 빈도로 샘플링하고,
각 시점에 어떤 함수 안에서 실행 중이었는지를 집계하는 방식입니다.

- [samply](https://github.com/mstange/samply) — `cargo install samply` 후
  `samply record ./target/release/myapp`를 실행하면 브라우저에서 결과를 볼 수 있습니다.
  macOS/Linux/Windows를 지원하므로 처음 사용할 프로파일러로 좋습니다
- `perf` — Linux에서 널리 쓰는 표준 도구입니다. samply나 flamegraph의 기반으로도 사용됩니다
- Instruments — macOS에 포함된 Xcode 기반 GUI 프로파일러입니다

프로파일 결과를 시각화할 때 자주 쓰는 방식이 **플레임 그래프**(flame graph)입니다.
가로 폭은 소비한 시간의 비율을 나타내고, 세로로 쌓인 박스는 함수 호출 관계를 보여 줍니다.
폭이 넓은 박스를 위로 따라가면 어떤 호출 경로가 시간을 많이 쓰는지 쉽게 찾을 수 있습니다.

release 빌드를 유지하면서 디버그 정보만 켜 두면
최적화된 성능을 유지하면서 프로파일러에서 함수 이름을 제대로 볼 수 있습니다.

```toml
[profile.release]
debug = true  # 최적화는 유지하고 심볼 정보만 추가합니다
```

## 하드웨어 카운터 — 왜 느린지 확인하기

프로파일러로 "이 함수가 느리다"는 사실을 찾았더라도
**왜** 느린지는 아직 모릅니다. 캐시 미스인지, 분기 예측 실패인지,
아니면 단순히 계산량이 많은 것인지 확인해야 합니다.
이때 사용하는 것이 CPU의 **하드웨어 성능 카운터**(hardware performance counter)입니다.
CPU에는 실행한 명령어 수, 캐시 미스 수, 분기 예측 실패 수 같은 값을 세는
전용 레지스터가 있습니다.

Linux에서는 `perf stat`으로 읽을 수 있습니다. 다음은 출력 예입니다.

```text
$ perf stat ./target/release/myapp
     4,381,297,063      instructions   #  1.02  insn per cycle
       912,438,571      branches
        41,282,946      branch-misses  #  4.52% of all branches
       102,381,842      cache-references
        38,472,013      cache-misses   # 37.6 % of all cache refs
```

읽는 방법은 Part I에서 배운 내용과 그대로 연결됩니다. 대략적인 기준은 다음과 같습니다.

- `insn per cycle`(IPC)이 낮다면 CPU가 무언가를 기다리고 있을 가능성이 큽니다.
  `cache-misses`가 많다면 메모리 대기(2장),
  `branch-misses`가 많다면 분기 예측 실패(3장)를 의심할 수 있습니다
- IPC가 해당 CPU의 이론적인 처리 한계에 가깝다면 실행 유닛이 비교적 잘 활용되고 있다는 뜻입니다.
  이 경우에는 명령어 수 자체를 줄이는 방향, 즉 알고리즘 개선이나 SIMD를 고려할 수 있습니다

다만 "몇이면 낮은 IPC인가"는 CPU와 명령어 구성에 따라 다릅니다.
또 `cache-misses` 같은 이벤트 이름이 정확히 어떤 하드웨어 사건을 세는지도 CPU마다 다를 수 있습니다.
많은 경우 마지막 수준 캐시 미스를 뜻하지만 실제 사용할 때는 `perf list`로
해당 CPU에서 제공하는 이벤트 정의를 확인해야 합니다.

macOS에서는 `perf`를 사용할 수 없고 Instruments의 "CPU Counters"가 비슷한 역할을 합니다.

## 어셈블리 — 무엇으로 컴파일됐는지 확인하기

마지막 도구는 컴파일 결과를 직접 보는 것입니다.
"벡터화됐을 것이다", "경계 검사가 사라졌을 것이다" 같은 가정은
어셈블리를 보면 바로 확인할 수 있습니다.

- [Compiler Explorer](https://godbolt.org/)(1장) — 작은 함수의 결과를 확인하기 좋습니다.
  Rust를 선택하고 `-O`를 지정합니다
- [cargo-show-asm](https://github.com/pacak/cargo-show-asm) — 로컬 크레이트의 함수를
  `cargo asm my_crate::my_fn`처럼 확인할 수 있습니다

어셈블리를 모두 읽을 필요는 없습니다.
4장에서처럼 루프에 `paddd`나 `vpaddd` 같은 SIMD 명령어가 보이는지,
`call` 명령이 남아 있는지처럼 큰 형태만 확인해도 충분한 정보를 얻을 수 있습니다.

## 최적화 우선순위

도구를 정리했으니 실제로 무엇부터 최적화할지 순서를 정해 보겠습니다.
위에 있을수록 대체로 효과가 크고, 아래로 갈수록 노력 대비 효과가 작아지는 경우가 많습니다.

1. **측정해서 병목 위치를 찾기** — 모든 최적화의 출발점입니다
2. **알고리즘과 자료구조** — O(n²)을 O(n log n)으로 바꾸는 개선보다 강력한 미세 최적화는 없습니다
3. **할당 줄이기** — `with_capacity`, `collect`, 버퍼 재사용(7장).
   웹 애플리케이션 계열 코드에서는 초기에 큰 효과를 내는 경우가 많습니다
4. **메모리 접근 패턴 정리하기** — 연속 접근, AoS→SoA, 데이터 크기 축소(2장)
5. **병렬화** — Rayon으로 나눌 수 있는 작업이라면 고려합니다(5장)
6. **SIMD와 저수준 조정** — 자동 벡터화가 잘 되는 형태로 바꾸고(4장),
   `target-cpu`, 프로파일 설정 등을 조정합니다(6장)
7. **unsafe를 이용한 최종 수단** — 경계 검사 제거 같은 방법입니다.
   측정으로 실제 병목이라고 확인된 경우에만 사용합니다

## 정리

- 추측은 자주 틀립니다. 측정 → 변경 → 재측정의 반복만이 신뢰할 수 있는 방법입니다
- 벤치마크에는 criterion을 사용합니다. `black_box`로 측정 대상이 사라지는 것을 막고,
  지연 평가와 debug 빌드에 주의해야 합니다
- 어디가 느린지는 프로파일러(samply), 왜 느린지는 하드웨어 카운터(`perf stat`),
  무엇으로 컴파일됐는지는 어셈블리(Compiler Explorer / cargo-show-asm)로 확인할 수 있습니다
- 우선순위는 알고리즘 → 할당 → 메모리 → 병렬화 → SIMD 순으로 생각하면 좋습니다

이것으로 Part II가 끝났습니다. CPU의 구조(Part I)와
Rust 컴파일러가 그 구조를 어떻게 활용하는지(Part II)를 함께 살펴봤습니다.
Part III에서는 설계 철학이 크게 다른 또 하나의 계산 장치인 GPU로 넘어갑니다.
지금까지 배운 CPU 지식은 GPU와 비교하는 기준으로 계속 활용됩니다.
